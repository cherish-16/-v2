## 1. 背景

团队成员的工作痕迹分散在 GitHub 提交、飞书任务流转与飞书群消息中。写日报时依赖下班后的回忆与逐平台复制粘贴，造成四类问题：条目遗漏（只写记得住的）、格式不一（组长需手工汇总）、协作成果归属不清（你帮我改的接口谁都没写）、无据可查（写的是印象不是事实）。

v2 用 Superpowers 工作流从零重新实现 v1 已完成的全部功能，目的是取得两套版本在工时、缺陷与质量上的可比数据（见 `docs/项目总结报告.md`）。**v2 不复制 v1 任何代码**，只继承文字性的设计结论。

## 2. 目标（均可度量）

| 编号 | 目标 | 度量指标 | 目标值 |
|---|---|---|---|
| G-01 | 日报自动化 | 需手工补写的成员占比 | ≤ 10%（每人每日手工补充 ≤ 1 条） |
| G-02 | 数据来源覆盖 | 采集成功的数据源数 / 计划数据源数 | = 3/3（GitHub、飞书任务、飞书消息） |
| G-03 | 条目可追溯率 | 可回溯到原始记录的条目 / 全部条目 | = 100% |
| G-04 | 生成时效 | 定时触发到推送完成耗时（≤ 10 人组） | ≤ 5 分钟 |
| G-05 | 稳定性 | 连续 5 个工作日定时任务成功率 | ≥ 95%（允许单模块失败降级） |
| G-06 | 格式一致性 | 团队日报符合统一模板的字段完整度 | = 100% |
| G-07 | 数据留存 | 日报历史可查询天数 | ≥ 90 天 |

## 3. 范围

### 3.1 做什么

| 编号 | 范围条目 | 说明 |
|---|---|---|
| R-01 | 采集 GitHub 提交记录 | 按 UTC 日区间、只读令牌、分页上限 |
| R-02 | 采集飞书任务流转 | 按日区间拉取任务状态变更 |
| R-03 | 采集飞书群消息 | 按日区间拉取群消息，撤回消息保留并标注 |
| R-04 | 生成个人日报 | 按成员归组，含无数据日标注 |
| R-05 | 生成团队日报 | 按成员分组汇总，格式统一，缺失成员显式标注 |
| R-06 | 邮件推送日报 | 逐收件人发送，部分失败隔离并返回结构化结果 |
| R-07 | 飞书机器人推送日报 | 群机器人 webhook 推送 |
| R-08 | SQLite 存储日报历史并支持查询 | 按日期 / 成员查询，保留 ≥ 90 天 |
| R-09 | 维护成员与采集映射配置 | 成员与 GitHub / 飞书账号映射，缺失不猜测 |
| R-10 | 定时触发全流程并保证幂等 | 同日同团队只允许一次成功运行 |
| R-11 | **采集飞书考勤数据并纳入日报**（v1.1 变更） | 按日区间采集出勤/缺勤记录，作为独立来源条目进入个人与团队日报 |

### 3.2 不做什么（本期明确排除）

| 编号 | 排除项 | 理由 |
|---|---|---|
| N-01 | 不做 AI 智能摘要 / 润色 | 生成内容不可核查，与"条目必须可追溯"冲突 |
| N-02 | 不做 Web 管理界面 | 本期以配置文件 + 命令行驱动，最小化实现面 |
| ~~N-03~~ | ~~不采集考勤数据~~ | **已由 R-11 变更纳入本期**（第 4 周变更单） |
| N-04 | 不做多团队租户隔离与权限体系 | 单团队部署，无多租户需求 |
| N-05 | 不做移动端 | 交付形态为定时任务 + 邮件/机器人 |

## 4. 技术约束

| 项 | 约束 |
|---|---|
| 语言 / 运行时 | Python 3.12+ |
| 依赖管理 | uv |
| HTTP 客户端 | httpx（统一，含超时与重试） |

## 5. 成功标准

### 5.1 功能验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| AC-01 | 三源采集可用 | 单日内三源均成功写入原始记录表 |
| AC-02 | 个人日报生成 | 条目完整、可追溯率 100%、无数据成员有标注 |
| AC-03 | 团队日报生成 | 按成员分组、格式统一、缺失成员显式标注 |
| AC-04 | 邮件推送 | 全部送达；单收件人失败不中断整批 |
| AC-05 | 飞书推送 | 群机器人推送成功且格式正确 |
| AC-06 | 定时与幂等 | 同日触发两次，第二次被忽略 |
| AC-07 | 历史查询 | 近 30 天查询结果正确，响应 ≤ 1 秒 |
| AC-08 | 安全合规 | 全仓无硬编码令牌，日志无敏感信息 |
| AC-09 | 规范一致性 | 代码与 `specs/` 无差异 |
| AC-10 | 考勤条目可追溯（v1.1） | 考勤条目 `source_type="feishu_attendance"` 且 `source_id` 非空，缺勤日有明确标注 |

### 5.2 性能验收

| 编号 | 指标 | 要求 |
|---|---|---|
| AC-P1 | 单成员日报生成 | ≤ 2 秒（原始记录 ≤ 500 条） |
| AC-P2 | 全流程（≤ 10 人） | ≤ 5 分钟 |

### 5.3 边界场景

| 编号 | 场景 | 期望行为 |
|---|---|---|
| AC-E1 | 当日全组无任何原始记录 | 仍生成日报并标注"无数据"，不返回空对象 |
| AC-E2 | 单一采集源认证失败 | 其余源继续，日报标注"来源缺失：<源>" |
| AC-E3 | 某成员未配置映射 | 跳过采集，日报标注"未配置映射成员"，不猜测归属 |
| AC-E4 | 团队日报生成中某成员失败 | 记入缺失成员，其余正常汇总 |
| AC-E5 | 全部推送渠道失败 | 保留已生成日报，摘要标记失败 |

## 6. 术语

| 术语 | 定义 |
|---|---|
| 原始记录 | 从外部系统采集、未经归组的提交 / 任务 / 消息数据 |
| 条目（ReportItem） | 日报中的一条工作描述，必须携带 `source_type` 与 `source_id` |
| 个人日报 | `scope=PERSONAL` 的 `DailyReport`，`entity_id` 为 member_id |
| 团队日报 | `scope=TEAM` 的 `DailyReport`，`entity_id` 为 team_id |
| 运行摘要（RunSummary） | 一次 `run_daily` 的采集 / 生成 / 推送结果汇总 |
| 映射配置 | 成员与 GitHub 账号、飞书账号的对应关系 |
| 端口（Port） | `Protocol` 定义的采集 / 推送抽象，真实与 Mock 实现可互换 |
