## 第 2 章 过程回顾

### 2.1 两阶段方法论执行

| 维度 | 阶段一（v1 · SDD） | 阶段二（v2 · Superpowers） |
|---|---|---|
| 规范产生方式 | proposal → design（含 ADR）→ tasks，人工主导，AI 辅助生成初稿 | 同样三份规范，但用 `brainstorming` 逐条澄清后落到 `writing-plans` 的 25 个任务 |
| 任务粒度 | 最终回填为 T-01~T-35 | 计划阶段即定为 T3-01~T3-18 + T4-01~T4-09，每任务一提交 |
| 编码方式 | 按规范逐任务生成，人工审查 diff | `executing-plans` + TDD：每任务先写失败测试、观察红灯、再实现 |
| 变更演练 | 无（v1 未做考勤变更） | 第 4 周做了完整的考勤变更涟漪演练 |
| 交付形态 | 含 Web 管理端（Vue 3）、Celery 定时、OAuth 登录 | 纯命令行 + 四层核心，无 Web |

### 2.2 两种方法的对比体会

**SDD 的优势**：规范写得更充分（v1 的 design.md 512 行、tasks.md 150 行），
尤其是 UML 附件、接口契约的细节。适合"先把问题想清楚"的阶段。

**Superpowers 的优势**：TDD 是硬约束，直接暴露了 4 个真实缺陷（见第 3 章），
这些缺陷在"先写实现再补测试"的模式下很可能不会被发现。

**主要成本差异**：v2 的环境搭建（依赖下载、`tzdata` 缺失）耗时占比明显高于编码本身；
v1 则因为要搭 Web + Celery + OAuth，总体面更大。

**结论**：对于"接口清晰、逻辑确定"的系统，TDD 流程收益最大；对于"探索性界面设计"，
先做原型更合适。

## 第 4 章 AI 使用与合规总结

| 环节 | AI 参与 | 人工核验 |
|---|---|---|
| 规范撰写 | 生成初稿、ADR 备选项 | 逐条确认，范围与"不做什么"由人定 |
| 任务拆解 | 建议粒度与依赖图 | 核对每条验收标准可执行 |
| 代码实现 | 按 TDD 任务生成 | 每个任务观察红灯→绿灯，审查 diff |

## 第 5 章 职业道德与行业规范践行心得

1. **诚实高于完整**。报告中 4 项指标标注"未测"，而不是编一个看起来漂亮的数字。
   课程把"伪造测试结果"列为黑级，其边界往往不是刻意造假，而是"顺手写个大概"。
2. **规范是承诺，不是装饰**。考勤变更时先改 proposal 与 design 再写代码，
   过程比"先写代码后补文档"慢，但改了什么、为什么改，事后能逐条追溯。
3. **可追溯性是设计出来的**。`source_id` 非空、`TraceabilityError` 都是刻意的约束，
   它让"日报里每条东西都能找到出处"成为代码保证，而非口头承诺。
4. **密钥与隐私是底线**。令牌只从环境变量读、日志邮箱脱敏、失败原因只记异常类型，
   这些在正常运行时"看不见"，但正是它们决定了系统出事时会不会连带泄露。
