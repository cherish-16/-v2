## 第 1 章 项目回顾（目标达成逐条对照）

### 1.1 项目要解决的真问题

团队成员的工作痕迹分散在 GitHub 提交、飞书任务流转与飞书群消息中。下班写日报靠回忆加逐平台复制粘贴，造成四类典型问题：

- **条目遗漏**——只写"记得住的"，不写"做了的"；
- **格式不一**——每人各写各的，组长需手工汇总；
- **协作成果归属不清**——"你帮我改的接口"谁都没写进日报；
- **无据可查**——写的是印象而不是事实。

本项目的目标是让日报从真实工作数据中"自动长出来"：按"采集层 → 生成层 → 推送层 → 主编排入口"四层构建，通过 GitHub API 与飞书开放平台采集提交、任务流转与群消息，自动生成个人与团队日报，经邮件与飞书机器人推送，SQLite 留存历史。同一项目按两种方法各完整实现一遍：阶段一用 SDD，阶段二用 Superpowers，从零重做、不复制代码，以获得两套版本在工时、缺陷与质量上的可比数据。

## 第 2 章 过程回顾

### 2.1 两大阶段方法论执行情况

| 维度 | 阶段一（v1 · SDD） | 阶段二（v2 · Superpowers） |
|---|---|---|
| 主导方法 | SDD 六阶段工作流：proposal → design → 接口契约 → tasks → 代码生成 → 验证交付 | Superpowers 工作流：brainstorming → writing-plans → executing-plans → TDD → systematic-debugging → code-review |
| 规范产生方式 | 三份规范 + UML 附件，人工主导、AI 辅助生成初稿；design.md 含 4 份 ADR | 同样三份规范，但先用 `brainstorming` 逐条澄清隐含需求，再落到 `writing-plans` 的任务清单；design.md 含 5 份 ADR |
| 任务粒度 | 任务清单按"项目结构→共享基础层→三采集模块→日报生成→推送→主编排→集成测试"组织 | 计划阶段即把任务定为"一任务=一可验证交付物"，含验收标准与依赖图 |
| 编码方式 | 按规范逐任务生成，人工审查 diff | TDD 红绿循环：先写接口约定与失败测试（红）→ 生成实现（绿）→ 重构；禁止先写实现再补测试 |
| 提交纪律 | 小步提交，message 规范 | 一次提交对应一个任务，`feat\|fix\|test\|docs: [任务编号] 一句话说明` |
| 变更演练 | 无 | 第 4 周完成考勤采集的完整变更涟漪演练（见 2.4） |
| 交付形态 | 含 Web 管理端、Celery 定时、OAuth 登录、LLM 生成 | 纯命令行 + 四层核心，无 Web、无 LLM |

### 2.2 两种方法完成同一项目的对比体会

**SDD 的优势——规范更充分**。v1 的 design.md 与 tasks.md 篇幅更大，UML 附件（用例图、类图、ER 图、数据流图）与接口契约写得更细。它逼你"先把问题想清楚"：范围条目、成功标准、5 份 ADR 的备选项与理由，都在写代码前固化。对探索期、界面与交互不确定的系统，这种"先想清楚再做"很合适。代价是规范与代码容易脱节——规范写得再多，若没有强制手段，实现仍可能悄悄偏离。

**Superpowers 的优势——质量内建**。TDD 是硬约束而非口号：每个任务必须先有失败测试。这一约束直接暴露了 4 个真实缺陷（见第 3 章），它们在"先写实现再补测试"的模式下很可能不会被发现——因为补测试时人会不自觉地"迁就实现"。brainstorming 把隐含需求问出来、writing-plans 把验收标准立在编码前，让"规范可执行"真正落地。

**主要成本差异**。v2 的环境搭建（依赖下载、Windows 缺 `tzdata` 导致时区回退 UTC）耗时占比明显高于编码本身；v1 因要搭 Web + Celery + OAuth + LLM 接入，总体面更大、集成点更多。

**结论**。对"接口清晰、逻辑确定"的系统（采集→归组→渲染→推送这类数据管道），TDD 流程收益最大——验收标准即测试，缺陷在红灯阶段暴露；对"探索性界面设计"（v1 的管理端），先做原型、规范后置更合适。两者不是替代关系：v2 的 design.md 同样包含完整 ADR 与接口契约，只是用 TDD 把"规范可执行"这一原则落到了实处。

### 2.3 角色轮换与贡献记录

> 本项目为**单人完成**，未执行指导书要求的五人角色轮换（需求分析师 / 架构师 / 开发工程师 / 测试工程师 / 配置管理员）。各角色的产出物（proposal/ADR/实现/测试/规范入库）由同一人按周次侧重分别承担。故个人贡献系数取基准 1.0，无组内互评与互评审。此项在多人组中须按指导书要求逐周填写轮换记录，作为个人成绩依据。

### 4.3 合规要点

1. **数据非估算**。测试数、覆盖率、提交数、行数均由附录 A 命令当场生成；无法核实的项明确标注"未测/未测得"。
2. **发现并更正数据错误**。过程中发现早期文档把 v1 测试数误记为 127（实测 73），予以更正。更正行为本身即对"伪造测试结果"红线的规避。
3. **规范是"人类领地"**。`specs/` 的修改建议由 AI 提出、由人确认后才提交；范围条目（含 5 条"不做什么"）由人确定，ADR 由 AI 列备选项、人做决策。
4. **重要结论三源核验**。如飞书接口字段结构（官方文档 + Mock 测试夹具 + 采集器映射代码）、GitHub 分页语义（官方文档 + 实现 + 测试用例）、重试策略（ADR-003 + `net.py` + `test_net.py`）。

## 第 5 章 职业道德与行业规范践行心得

1. **诚实高于完整**。报告中 3 项指标标注"未测"、v1 覆盖率标注"未测得"，而非编一个看起来漂亮的数字。课程把"伪造测试结果"列为黑级，其边界往往不是刻意造假，而是"顺手写个大概"。本次发现旧文档把 v1 测试数误记为 127（实测 73）后予以更正，正是这条底线的践行——比起一个好看但错误的数字，一个真实但平凡的数字更有职业价值。

2. **规范是承诺，不是装饰**。考勤变更时先改 proposal 与 design 再写代码，过程比"先写代码后补文档"慢，但改了什么、为什么改，事后能逐条追溯。"规范先行"在变更演练中体现得最清楚：任何一处规范与代码未同步即记为缺陷。

3. **可追溯性是设计出来的，不是说出来的**。`ReportItem.source_id` 非空、`TraceabilityError`、条目 `source_type` 强制，都是刻意约束。它们让"日报里每条东西都能找到出处"成为代码保证，而非口头承诺——这正是对"日报形式化、内容空泛"这一真问题的工程回应。

4. **密钥与隐私是底线**。令牌只从环境变量读、禁止入库入仓；日志对 token 与邮箱脱敏；失败原因只记异常类型不记敏感内容；GitHub 令牌只读 scope。这些在正常运行时"看不见"，但正是它们决定系统出事时会不会连带泄露。

5. **对"不做什么"负责**。v2 明确排除 AI 智能摘要（生成内容不可核查，与"条目必须可追溯"冲突）、Web 界面、多租户、移动端。把"不做什么"写进规范并坚守，和实现功能一样是工程师的责任——它防止范围蔓延，也让成功标准保持可度量。

## 第 6 章 不足与改进

| 不足 | 原因 | 改进方向 |
|---|---|---|
| 真实 API 未联调 | 无可用凭证 | 拿到凭证后跑 `source_mode=live` 冒烟 |
| 性能与稳定性指标（G-01/G-04/G-05）未测 | 缺真实数据量与环境 | 用真实历史数据回放，连续运行统计 |
| v1 覆盖率未测得 | v1 虚拟环境无 pip，装不了 coverage | 用 `uv pip` 补装或重建 v1 环境后测 |
| 90 天留存（G-07）未实现 | 本期范围未含清理任务 | 加 `retention.py` + 定时清理任务 |
| 定时调度未接入 | v2 仅提供 CLI | 注册系统计划任务或在部署文档给出 crontab/systemd |
| v2 无 Web 界面 | proposal N-02 明确排除 | 若需要须走范围变更流程 |
| 单人完成，未做角色轮换 | 项目条件 | 多人组须按指导书补轮换记录 |
