> 本报告记录两阶段的技术调研过程：候选方案、对比依据、最小验证与选型结论。所有结论均可回溯到对应的 ADR；未经演示验证的结论标注为"文档推断"，不冒充实测。

## 第 1 章 调研背景与范围

### 1.1 要解决的技术问题

系统与四类外部系统打交道：GitHub REST API（提交记录）、飞书开放平台（任务流转、群消息、考勤）、邮件（SMTP）与飞书群机器人（webhook）。核心负载特征是 **I/O 密集而非计算密集**——瓶颈在外部接口的等待、限流与失败重试，不在自身吞吐。由此，调研聚焦在五个问题：

1. 用什么 HTTP 客户端统一调用多个平台，并兼顾异步并发与可测试性？
2. 用什么存储持久化原始记录、日报与运行摘要，且在单机答辩环境可复制？
3. 如何接入外部平台（GitHub / 飞书 / 邮件 / 机器人），又不在测试与演示时依赖真实凭证？
4. 外部 API 的限流与瞬时故障如何处理，才能既不自放大故障、又不因抖动导致数据缺失？
5. 定时调度与幂等如何实现，才能"同日同团队只成功运行一次"？

### 1.2 调研范围与非范围

| 类别 | 内容 |
|---|---|
| 调研范围 | HTTP 客户端、存储、外部平台接入方式、重试策略、调度与幂等、测试替身方案 |
| 阶段一（v1）额外范围 | 大模型接入（统一 `LLMProvider` 抽象）、Web 管理端框架、缓存与任务队列 |
| 非范围 | 前端 UI 设计细节、UI 交互美学、多租户权限体系、移动端 |
| 硬性约束 | Python 3.12+、uv 依赖管理、凭证仅环境变量注入、ruff 零告警、测试先行 |

### 1.3 两阶段调研口径的差异

同一条技术主线调研了两次，但口径不同：

- **阶段一（v1）** 面更大：要选 LLM 供应商、Web 框架、缓存与队列，因此调研了 7 个技术域，落地为 4 份 ADR。
- **阶段二（v2）** 面收窄：明确排除 LLM 与 Web（见 `Reportv2/specs/proposal.md` N-01/N-02），只保留"采集→生成→渲染→推送"数据管道所需的选型，但把"重试分流""端口适配器""变更接入手法"三处做得更细，落地为 5 份 ADR。

## 第 2 章 候选技术对比

### 2.1 架构形态（v1 调研）

| 备选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **模块化单体 + 异步任务（采纳）** | 一次部署、调试简单；按采集/生成/推送/汇总划分边界，后续可拆 | 共享进程与数据库，单点故障影响面大 | v1 采纳 |
| 微服务 | 独立部署扩容、故障隔离 | 课程周期内联调与运维成本过高，<5 人团队收益为负 | 否决 |
| Serverless / 云函数 | 免运维、按量计费、天然弹性 | 冷启动延迟、执行时长受限、平台锁定 | 否决 |
| 单机脚本 + 定时 | 最快出原型 | 无多用户、无权限、无持久化查询 | 仅用于原型验证 |

核心理由：本项目的复杂度来自外部集成（飞书权限、数据清洗），而非内部服务拆分；课程周期内微服务只增成本、不增收益。

### 2.2 HTTP 客户端

| 备选项 | 优点 | 缺点 | 结论（v1 / v2） |
|---|---|---|---|
| **httpx** | 同步/异步双 API；原生 `MockTransport` 注入测试响应；超时/重试/HTTP2 配置齐全 | 生态小于 requests；需熟悉 async | 两阶段均采纳 |
| requests | 最普及、示例多 | 不支持 async，并发需线程池；与异步链路不匹配 | 否决 |
| aiohttp | 性能好、异步成熟 | API 偏底层，连接管理与 mock 需额外封装 | 否决 |
| 各平台官方 SDK | 字段映射省事 | 飞书/GitHub 两套 SDK 异常模型不一；版本受制于 SDK | 部分采纳：仅在明显降复杂度时包装为适配器 |

两阶段结论一致，但理由侧重不同：v1 强调"异步链路 + FastAPI/Celery 集成"，v2 强调"`MockTransport` 可直接注入、无需 monkeypatch 网络栈"，即**可测试性**成为首要依据。

### 2.3 存储

| 备选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **SQLite（v1：SQLAlchemy+Alembic；v2：标准库 sqlite3 手写参数化）** | 零运维、单文件、随目录复制；JSON 函数与 FTS5；答辩可拷走完整复现 | 并发写弱；多实例有锁竞争 | 两阶段均采纳，实现方式不同 |
| PostgreSQL | 并发与事务强，适合多实例 | 需额外部署；答辩环境多一依赖 | 否决（本规模用不上） |
| MySQL | 普及度高 | 同样需独立服务；JSON 能力较弱 | 否决 |
| 仅文件（JSON/CSV） | 实现最快 | 无事务、无查询与并发能力 | 否决（撑不起状态机与审计） |

实现方式的差异是本报告最有价值的对比点：

- **v1** 用 ORM（SQLAlchemy 2.0 + Alembic 迁移），适合表结构演进与 Web 多模块协作；
- **v2** 直接 `sqlite3` + 手写参数化 SQL，理由见 ADR-002：数据量远低于 SQLite 上限、零额外依赖、**显式 SQL 便于逐条审查参数化**（现场答辩时 SQL 可见性更重要）、ORM 在本规模引入抽象成本。

两者共同约束：开启 `journal_mode=WAL` 与 `foreign_keys=ON`，写操作串行，`DATABASE_URL` 作为唯一切换点。

### 2.4 外部平台接入方式

这是两阶段差异最大的一域，也正是 v2 ADR-004 的核心决策点。

| 备选项 | 优点 | 缺点 | 结论（v2） |
|---|---|---|---|
| **端口 + 真实/Mock 双实现（采纳）** | 真实与模拟逻辑互不污染；测试可直接注入替身；配置一行切换 | 多一套实现成本 | v2 采纳 |
| 真实实现内嵌 `if mock` 分支 | 实现最省 | 真实与模拟逻辑互相污染，无法独立测试 | 否决 |
| 只做 Mock | 无需凭证 | 交付物不完整，无法证明真实接入可用 | 否决 |

结论：以 `Protocol` 定义采集/推送端口，真实与 Mock 实现共享同一契约，由 `Settings.source_mode` 切换。这既满足"第 0 周凭证可能未就绪时仍可演示"的现实约束，也保证测试与演示不依赖真实外部系统。

### 2.5 重试策略（v2 ADR-003）

| 备选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **按异常类型分流（采纳）** | `TransientError`（超时/5xx/429）最多重试 2 次、退避 1s/2s；`AuthenticationError` 不重试 | 需区分异常类型 | v2 采纳 |
| 全部统一重试 | 实现最简单 | 把 401 放大成 3 倍无效请求，延长故障 | 否决 |
| 不重试 | 不放大故障 | 瞬时抖动直接造成来源缺失 | 否决 |

### 2.6 调度与幂等

| 备选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **v1：Celery Beat + Redis** | 定时、重试、任务状态成熟；可与 FastAPI 共享配置 | 组件重、调试成本高；Windows 需 Docker | v1 采纳 |
| **v2：系统计划任务 + CLI** | 零额外组件，契合纯 CLI 形态 | 任务状态不可查，重试需自建 | v2 采纳 |
| APScheduler（进程内） | 零额外组件 | 多实例重复执行，无持久化与重试 | 否决 |
| 系统 cron + CLI（v1 视角） | 简单直观 | 任务状态不可查、重试与并发需自建 | v1 否决 / v2 采纳 |

幂等在两个阶段都用**数据库唯一约束**保证：v1 用 `run_key`，v2 用 `run_summaries(team_id, run_date, status)` 成功唯一。差别在于 v1 额外要"可展示的任务状态与重试记录"（验收证据），故引入 Celery；v2 无 Web 无状态看板需求，cron + CLI 更贴合。

### 2.7 大模型接入（仅 v1）

| 备选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **统一 `LLMProvider` + 默认国内模型（采纳）** | 可切换供应商；测试注入 FakeProvider；业务不感知厂商 | 多一层抽象与提示词适配 | v1 采纳 |
| 直接调用单一厂商 SDK | 代码最短 | 供应商锁定；测试需联网 | 否决 |
| 自部署开源模型 | 数据不出域 | 需 GPU 与运维，课程周期不可行 | 否决（后续私有化选项） |

v2 因"LLM 生成内容不可核查、与条目可追溯冲突"（proposal N-01）而整体放弃 LLM，改为模板化生成——这本身也是一次技术选型的**反向验证**：抽象层能把生成方式的变化隔离，但"是否需要不可核查的生成"是产品与合规问题，不是技术问题。

### 2.8 Web 管理端与缓存队列（仅 v1）

| 技术域 | 采纳 | 主要否决项 |
|---|---|---|
| 管理端前端 | Vue 3 + TypeScript + Vite + Element Plus | React（生态更大但概念多）；纯消息卡片（交互不足） |
| 缓存/队列 | Redis + Celery | ARQ/RQ（定时能力弱）；RabbitMQ/Kafka（过度设计） |

同理，v2 明确排除 Web（proposal N-02），故该域在阶段二不再调研。

### 2.9 候选技术汇总表

| 技术域 | v1 选择 | v2 选择 | 对应 ADR |
|---|---|---|---|
| HTTP 客户端 | httpx | httpx | v1-ADR-001 / v2-ADR-001 |
| 存储 | SQLite + SQLAlchemy/Alembic | SQLite + 标准库 sqlite3 手写参数化 | v1-ADR-002 / v2-ADR-002 |
| 生成方式 | 统一 LLMProvider（默认 DeepSeek） | 模板化，无 LLM | v1-ADR-003 / v2-ADR-001(N-01 反向) |
| 平台接入 | 适配器 + Mock 模式 | 端口 + 真实/Mock 双实现 | v2-ADR-004 |
| 重试 | 客户端层统一配置 | 按异常类型分流 | v2-ADR-003 |
| 调度 | Celery + Redis | 系统计划任务 + CLI | v1-ADR-004 |
| 考勤接入 | —（未涉及） | 独立 AttendanceSource Protocol | v2-ADR-005 |

## 第 3 章 关键技术验证（最小实验与 PoC 记录）

本章记录三条最关键的"能不能行"验证。凡未实际执行、仅据文档推断的，明确标注。

### 3.1 PoC-1：`httpx.MockTransport` 注入测试响应

**验证目标**：能否在不联网、不 monkeypatch 网络栈的前提下，用固定 JSON 驱动采集器全部分支（分页、短页停止、空区间、认证失败）。

**做法**：构造 `httpx.MockTransport(handler)`，handler 按请求 URL 与查询参数返回预置响应；采集器持有 `httpx.Client(transport=...)`。

**结果**：可行。采集器的分页循环、短页终止、空区间返回 `[]`、401 抛 `AuthenticationError` 等路径均由该方式覆盖（见 v2 `tests/test_github_collector.py`、`tests/test_feishu_collector.py`）。**此验证同时暴露了缺陷 DI-002（短页未停止）与 DI-003（测试数据不足以触发第 2 页）**——正是 PoC 先行的价值。

**对选型的影响**：把"可测试性"确立为 HTTP 客户端的首要依据，requests/aiohttp 因 mock 成本更高被否决。

### 3.2 PoC-2：SQLite 在单机演示下的参数化与 WAL 表现

**验证目标**：手写参数化 SQL 能否满足"全参数化 + 并发读 + 单进程串行写 + 数据可整体拷贝"。

**做法**：v2 用标准库 `sqlite3` 建表，开启 `PRAGMA journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=5000`；原始记录表 `INSERT OR IGNORE` 按主键去重；所有查询参数化。

**结果**：可行，且**无需 ORM**。显式 SQL 让"SQL 只出现在存储层"这一分层约束可被 `test_architecture.py` 静态检查；WAL 支持读写并发，busy_timeout 吸收短时锁竞争。约束是"多实例部署前必须迁移 PostgreSQL"，已在 ADR 中作为已知边界写明。

**说明**：并发压力（多人同时写）不在本项目范围，未做压测；此为范围约束，而非遗漏。

### 3.3 PoC-3：重试分流的可观测性

**验证目标**：按异常类型分流（`TransientError` 重试、`AuthenticationError` 不重试）能否用测试断言钉死每条路径。

**做法**：`net.py` 按异常类型决定重试；`tests/test_net.py` 覆盖 6 条路径（首次成功、超时后成功、5xx 后成功、429 后成功、401 直接失败、重试耗尽失败）。

**结果**：可行。6 条路径断言全绿，分流逻辑与 ADR-003 一一对应。这也印证了一个通用结论：**"重试策略"这类看似简单的决策，一旦按异常类型分流，就值得用测试逐条固化**，否则"该重试的没重试、不该重试的放大了"这类问题会在集成期才暴露。

### 3.4 未做（或无法做）的验证

| 验证项 | 状态 | 原因 |
|---|---|---|
| 真实飞书 / GitHub API 联调 | 未做 | 无可用凭证，仅有 Mock 路径 |
| 全流程耗时与连续成功率 | 未测 | 无真实数据量与时间跨度 |
| 多实例并发写 SQLite | 未做 | 不在本期范围（单机部署） |
| 大模型生成质量评测（v1） | 未做 | 需真实调用与标注数据，超出本期条件 |

诚实标注这些空白，是为了让"已验证"的结论不被误读为"全部已证实"。

## 第 4 章 选型结论（与 design.md 中 ADR 对应）

### 4.1 v1 的 4 份 ADR

| ADR | 决策 | 备选项中被否决者 | 关键理由 |
|---|---|---|---|
| v1-ADR-001 | HTTP 客户端用 `httpx.AsyncClient`，按数据源一实例，超时/重试/限流在客户端层配置 | requests（无 async）、aiohttp（mock 成本高）、官方 SDK（异常模型不一） | 异步并发 + `MockTransport` 同时解决性能与可测试性 |
| v1-ADR-002 | SQLite 单文件，WAL + `busy_timeout=5000` + 外键；写集中在 Worker 串行 | PostgreSQL / MySQL（多一依赖）、纯文件（无事务与查询） | 复杂度在外部集成而非数据规模；部署依赖降到最低 |
| v1-ADR-003 | 统一 `LLMProvider`（`generate(prompt, schema, timeout) -> str`），默认 DeepSeek，测试用 FakeProvider | 单一厂商 SDK（锁定）、自部署模型（GPU 成本） | 生成质量与合规是易变项，抽象层隔离变化 |
| v1-ADR-004 | Celery Beat 触发 + Worker 执行，`run_key` 保证幂等 | APScheduler（重复执行）、cron+CLI（状态不可查） | 验收需可展示的任务状态、重试与幂等证据 |

### 4.2 v2 的 5 份 ADR

| ADR | 决策 | 备选项中被否决者 | 关键理由 |
|---|---|---|---|
| v2-ADR-001 | HTTP 客户端用 `httpx` | requests（缺 MockTransport 便利）、urllib（代码量最大） | `MockTransport` 可直接注入，无需 monkeypatch 网络栈 |
| v2-ADR-002 | 标准库 `sqlite3` + 手写参数化 SQL，零 ORM | SQLAlchemy+Alembic（抽象成本）、JSON 文件（无查询/并发） | 数据量小；显式 SQL 便于逐条审查参数化，答辩时 SQL 可见 |
| v2-ADR-003 | 按异常类型分流重试：Transient 最多 2 次退避 1s/2s，Auth 不重试 | 全部重试（放大 401）、不重试（抖动致缺源） | 以最小代价覆盖两类真实故障 |
| v2-ADR-004 | 端口 + 真实/Mock 双实现，`Settings.source_mode` 切换 | 内嵌 `if mock` 分支（互相污染）、只做 Mock（不完整） | 双实现共享同一 Protocol，测试可注入替身 |
| v2-ADR-005 | 新增独立 `AttendanceSource` Protocol，`SourceBundle` 加可选字段 | 改既有 `collect_tasks` 签名（违反单一职责）、生成层直接读库（破坏分层） | 与既有端口模式一致，可选字段保证未配置时零影响 |

### 4.3 两套结论的一致性

三个技术域两阶段独立得出**相同或兼容**的结论：

| 技术域 | v1 与 v2 是否一致 | 说明 |
|---|---|---|
| HTTP 客户端 | 完全一致（httpx） | 独立调研、独立否决 requests |
| 存储引擎 | 一致（SQLite） | 仅封装方式不同（ORM vs 手写 SQL） |
| 平台接入 | 兼容（适配器/端口模式） | v1 称"适配器 + Mock 模式"，v2 称"端口 + 双实现"，本质同一模式 |
| 调度 | 不同但各有依据 | v1 需状态看板故用 Celery；v2 纯 CLI 故用 cron |
| 重试 | v2 更细 | v1 在客户端层统一配置，v2 明确按异常类型分流 |

"同一技术域两次独立调研得出同一结论"本身是选型质量的旁证；而调度域的差异恰好说明：**选型应绑定具体交付形态与验收证据，而非追求唯一正确答案**。

## 第 5 章 风险与约束

### 5.1 已识别风险与缓解

| 编号 | 风险 | 影响 | 缓解措施 | 状态 |
|---|---|---|---|---|
| RK-01 | 真实 API 未联调 | 真实凭证下的字段/权限/限流行为未知 | 端口化设计，Mock 与真实同契约；拿到凭证后跑 `source_mode=live` 冒烟 | 未验证 |
| RK-02 | 飞书凭证 / SMTP 授权码未就绪 | 无法演示真实推送 | Mock 双实现 + 配置切换（ADR-004） | 已缓解 |
| RK-03 | SQLite 多实例并发写锁竞争 | 多实例部署数据冲突 | 单机部署；`busy_timeout`；多实例前迁移 PostgreSQL（ADR-002 已写明边界） | 已知边界 |
| RK-04 | 外部 API 限流 / 瞬时故障 | 来源缺失、日报不完整 | 按异常类型分流重试（ADR-003）+ 单源失败不中断、来源标注缺失 | 已实现 |
| RK-05 | 凭证泄露 | 安全合规风险 | 仅环境变量注入；日志 token/邮箱脱敏；令牌只读 scope；`git grep` 扫描（红级红线） | 已实现 |
| RK-06 | 依赖版本 / 平台差异（Windows 缺 tzdata） | 时区回退 UTC，时间窗口错位 | 显式安装 `tzdata`；时间统一 UTC aware，naive datetime 抛 `ValueError` | 已修复（DI-005） |
| RK-07 | LLM 生成内容不可核查（v1） | 生成内容无法追溯 | v2 否决 LLM，改模板化（N-01）；v1 中 LLM 结果须可回溯且失败降级模板 | 架构决策 |

### 5.2 硬性约束（不可协商）

| 类别 | 约束 | 落地方式 |
|---|---|---|
| 运行时 | Python 3.12+、uv 依赖管理 | `pyproject.toml` + `uv.lock` |
| 凭证 | 仅环境变量注入，禁止入库入仓 | `config.py` 唯一读取点；`.env` 被 gitignore |
| SQL | 全参数化，仅存储层写 SQL | `repository.py` 单点；`test_architecture.py` 检查 |
| 分层 | 下层不得 import 编排层 | `test_architecture.py` 自动检查 |
| 质量 | ruff 零告警、测试先行 | CI 门禁；TDD 红绿循环 |
| 可追溯 | 条目 `source_id` 非空 | `TraceabilityError` 强制 |
| 时间 | 区间 `since` 含、`until` 不含，UTC aware | naive datetime 抛 `ValueError` |

### 5.3 技术债与后续演进

| 技术债 | 当前选择 | 演进路径 |
|---|---|---|
| 无 Web 界面（v2） | 纯 CLI | 需 Web 时走范围变更，复用四层端口 |
| 未接定时调度（v2） | 仅 CLI | 注册系统计划任务 / systemd / crontab |
| 90 天留存未实现 | 仅查询不清理 | 加 `retention.py` + 定时清理任务 |
| 大模型生成（v1） | 默认 DeepSeek，抽象可切换 | 私有化部署时替换 Provider 实现 |
| 单实例 SQLite | 单机演示 | 多实例前迁 PostgreSQL，仅改 `DATABASE_URL` |

**总结**：本项目的技术选型始终围绕"I/O 密集、单机演示、可追溯、可测试"四条主线。两阶段独立调研在核心三域（HTTP/存储/接入）收敛到同一结论，差异域（调度、生成方式、重试粒度）均可由**交付形态与验收证据**解释——这正是"规范驱动、结论可回溯"在技术选型上的体现。
