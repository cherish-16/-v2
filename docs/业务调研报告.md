## 一、调研概述

### 1.1 项目背景

日报是团队同步进展、暴露风险、沉淀过程资产的基础管理动作。传统手工日报存在四类问题：

1. **条目遗漏**：员工凭回忆填写，容易漏掉跨平台、跨项目的真实产出；
2. **格式不一**：不同成员写法差异大，负责人汇总耗时；
3. **归属不清**：协作成果（如帮人 review 接口、共同推进任务）在日报中难以体现；
4. **无据可查**：日报内容变成“印象”而非可追溯的事实记录。

### 1.2 调研目的

- 验证“自动生成日报”是否为真实、高频的需求；
- 明确目标用户、核心痛点与使用场景；
- 摸清竞品能力边界，找到差异化定位；
- 为后续需求规格、技术选型与实现范围提供业务依据。

### 1.3 调研方法

| 方法 | 对象/范围 | 产出 |
|---|---|---|
| 桌面研究 | 行业报告、飞书/钉钉开放平台文档、竞品公开资料 | 市场趋势、竞品功能矩阵 |
| 用户访谈 | 研发、产品、运营、团队负责人共 8 人（课程模拟） | 痛点、场景、现有替代方案 |
| 竞品体验 | 飞书汇报、钉钉日志、企业微信汇报、开源日报机器人 | 功能对比与差距分析 |
| 课程约束梳理 | 软件工程课程设计指导书 | 裁剪出可交付的 MVP 范围 |

### 1.4 课程 v2 范围裁剪说明（与完整产品愿景的差异）

本报告第 2~4 节保留“完整产品愿景”，用于说明市场机会；第 5 节起给出与本期实现严格对应的 **v2 CLI MVP 范围**。两者差异如下：

| 维度 | 完整产品愿景 | 本期工程实现（v2 CLI MVP） | 理由 |
|---|---|---|---|
| 产品形态 | 飞书生态内 SaaS / Web 应用 | Python CLI + Windows 批处理 + 系统定时任务 | 课程周期与交付形态约束（N-02） |
| 生成方式 | 大模型摘要 + 人工确认 | 模板化生成，无 LLM 参与 | 可追溯优先，LLM 输出不可核查（N-01） |
| 数据源 | 飞书日历/文档/任务/消息 + Git/Jira | GitHub 提交 + 飞书任务 + 飞书消息 + （v1.1 变更）飞书考勤 | 聚焦研发团队高频工作痕迹，最小可行闭环 |
| 用户界面 | Web 管理端、消息卡片编辑器 | 命令行参数 + 终端输出 + 邮件/机器人推送 | 最小化实现面 |
| 权限体系 | 部门隔离、角色权限 | 单团队、无权限体系（N-04） | 单团队部署 |

> 后续所有工程文档（需求分析、技术调研、系统分析、系统设计）均只描述“本期工程实现”范围，不展开完整产品愿景中的 Web / LLM / 多租户等远期能力。

## 二、市场与行业分析

### 2.1 行业趋势

1. **协作平台开放生态成熟**：飞书、钉钉、企业微信开放 API，使“从工作痕迹自动还原工作内容”具备工程可行性；
2. **企业数据治理趋严**：《数据安全法》《个人信息保护法》要求最小必要、可审计，推动“数据不出域、过程可追溯”的工具需求；
3. **AI 辅助办公兴起**：大模型可用于摘要与润色，但企业场景下“可核查性”比“生成质量”更关键；
4. **研发管理数字化**：Git、任务板、即时消息成为研发过程的事实记录，自动采集比人工回忆更可靠。

### 2.2 目标市场

- **核心市场**：已使用飞书的中小企业研发团队（10–100 人）；
- **次级市场**：使用钉钉/企业微信的研发团队、远程与分布式团队；
- **机会判断**：日报是普遍管理动作，现有产品自动化程度低，存在明确产品空位。

### 2.3 政策与合规环境

- 处理员工工作数据需遵循最小必要、目的限定、可审计原则；
- 企业侧普遍要求数据不出域、可删除、可追溯；
- 因此产品需支持：字段级脱敏、生成记录留存与审计日志、最小权限授权。

### 2.4 市场机会小结

需求普遍存在 + 现有方案自动化不足 + 平台能力已就绪 + 合规要求推动可控工具，构成本项目的市场机会窗口。竞争关键在于**数据采集完整度、生成内容可信度、与企业现有工作流融合度**。

## 三、用户研究

### 3.1 用户画像

| 角色 | 特征 | 核心诉求 | 使用频率 |
|---|---|---|---|
| 一线研发/产品/运营 | 22–35 岁，日常在飞书与研发工具中工作 | 少花时间写日报，内容真实不漏项 | 每日 |
| 团队负责人 | 管理 5–20 人 | 快速掌握进展与风险，减少催收 | 每日 |
| 教师/企业导师 | 关注规范与证据 | 统一格式、可导出、可追溯 | 每周/每月 |
| 配置管理员 | 运维者 | 凭证安全、部署简单 | 初始化/故障时 |

### 3.2 典型场景

1. **下班前自动推送**：系统按团队时区定时采集当天工作痕迹，生成团队日报并推送到邮件/飞书群；
2. **手动补推**：通过 `推送日报.bat` 或 CLI 手动触发，支持 `--force` 重跑；
3. **项目复盘**：负责人查看历史日报，识别阻塞项与跨人依赖；
4. **新人了解项目脉络**：通过历史日报快速回顾团队近期工作。

### 3.3 痛点归纳

| 编号 | 痛点 | 影响 | 现有替代方案不足 |
|---|---|---|---|
| P1 | 回忆当天工作耗时 | 每天 10–30 分钟 | 翻聊天记录、看提交记录，效率低 |
| P2 | 数据来源分散 | 容易漏项、内容不完整 | 手工拼接多个系统截图 |
| P3 | 格式不统一 | 管理者汇总困难 | 强制模板，员工抵触 |
| P4 | 日报形式化 | 内容空泛，失去管理价值 | 无有效手段 |
| P5 | 隐私顾虑 | 不愿暴露全部工作细节 | 拒绝使用或敷衍填写 |

### 3.4 需求优先级（MoSCoW）—— 本期工程实现

- **Must**：多源数据采集（GitHub、飞书任务、飞书消息、飞书考勤）、个人/团队日报生成、邮件/飞书机器人推送、成员映射配置、定时触发与幂等；
- **Should**：历史查询、失败隔离与来源缺失标注、运行摘要审计；
- **Could**：模板定制、周报/月报自动生成、多语言；
- **Won't（本期）**：AI 智能摘要/润色（N-01）、Web 管理界面（N-02）、多团队租户隔离（N-04）、移动端（N-05）、绩效评分/员工行为监控。

## 四、竞品分析

| 产品 | 数据来源 | 自动化程度 | 生成质量 | 部署/隐私 | 主要不足 |
|---|---|---|---|---|---|
| 飞书汇报/日报 | 手工填写 | 低 | 取决于员工 | SaaS | 无自动采集，仍靠人工 |
| 钉钉日志 | 手工填写 + 模板 | 低 | 取决于员工 | SaaS | 同上 |
| 企业微信汇报 | 手工填写 | 低 | 取决于员工 | SaaS | 同上 |
| Notion AI / 语雀 AI | 文档内容 | 中 | 较好 | SaaS | 依赖文档沉淀，不覆盖任务/代码/考勤 |
| 通用大模型 | 用户粘贴 | 低 | 好 | 数据出域 | 需手工喂数据，企业合规风险 |
| 开源日报机器人 | 单一源（如 Git） | 中 | 一般 | 可自部署 | 数据源单一，缺少产品化体验 |

**结论**：现有竞品的空白在于“**多源自动采集 + 企业内闭环 + 可追溯可核查**”。本期实现定位为“研发团队工作痕迹 → 日报”的自动化工具：不替代飞书，而是把 GitHub 与飞书里的工作痕迹变成结构化日报。

## 五、产品定位与需求范围（本期工程实现）

### 5.1 价值主张

- 对**每天要写日报的员工**：无需回忆，系统自动从工作痕迹生成条目；
- 对**团队负责人**：每天自动收到格式统一、按成员分组的团队日报，缺失成员与来源缺失显式标注；
- 对**企业/课程评审**：数据留在本地 SQLite，生成过程可审计，密钥不进入代码仓库。

### 5.2 功能需求（v2 CLI MVP）

| 编号 | 功能 | 对应范围条目 | 说明 | 优先级 |
|---|---|---|---|---|
| FR-01 | GitHub 提交采集 | R-01 | 按 UTC 日区间、只读令牌、分页上限 | P0 |
| FR-02 | 飞书任务流转采集 | R-02 | 按日区间拉取任务状态变更 | P0 |
| FR-03 | 飞书群消息采集 | R-03 | 按日区间拉取群消息，撤回消息保留并标注 | P0 |
| FR-04 | 飞书考勤采集 | R-11 | 按日区间采集出勤/缺勤/迟到/请假 | P0 |
| FR-05 | 个人日报生成 | R-04 | 按成员归组，含无数据日标注 | P0 |
| FR-06 | 团队日报生成 | R-05 | 按成员分组汇总，格式统一，缺失成员显式标注 | P0 |
| FR-07 | 邮件推送日报 | R-06 | 逐收件人发送，部分失败隔离并返回结构化结果 | P0 |
| FR-08 | 飞书机器人推送日报 | R-07 | 群机器人 webhook 推送 | P0 |
| FR-09 | 日报历史存储与查询 | R-08 | SQLite 持久化，按日期/成员查询 | P0 |
| FR-10 | 成员与采集映射配置维护 | R-09 | 成员与 GitHub / 飞书账号映射，缺失不猜测 | P0 |
| FR-11 | 定时触发全流程并保证幂等 | R-10 | 同日同团队只允许一次成功运行 | P0 |

### 5.3 非功能需求

- **性能**：单成员日报生成 ≤ 2 秒；全流程（≤ 10 人）≤ 5 分钟；历史查询 ≤ 1 秒；
- **可用性**：单源失败不中断整批，缺失来源写入日报 note；无数据日仍生成并标注；
- **安全**：最小权限授权、凭证仅环境变量注入、日志脱敏、参数化 SQL；
- **可扩展**：数据源以端口/适配器模式接入，便于后续扩展；
- **合规**：采集范围仅限团队成员工作账号，数据本地存储。

### 5.4 业务流程（本期）

```text
定时任务 / 手动触发
        │
        ▼
   多源数据采集（GitHub / 飞书任务 / 飞书消息 / 飞书考勤）
        │
        ▼
   数据清洗与成员归组（attribution）
        │
        ▼
   模板化生成个人日报 + 团队日报
        │
        ▼
   渲染并推送（邮件 + 飞书机器人）
        │
        ▼
   运行摘要落库与历史归档
```

## 六、可行性分析

### 6.1 技术可行性

- **平台能力**：GitHub REST API、飞书开放平台任务/消息/考勤接口已开放；
- **工程复杂度**：核心难点在数据采集的窗口换算、归组与失败隔离，采用分层 + 端口适配器可控制复杂度；
- **风险点**：平台 API 限流、权限审核周期、凭证未就绪时的演示问题——已通过 Mock 双实现缓解。

### 6.2 经济可行性（课程视角）

- 本期实现无 LLM 调用成本；
- 依赖以标准库与 `httpx` 为主，无额外商业组件；
- 单机 SQLite 部署，无服务器费用。

### 6.3 运营可行性

- 推广路径：本地部署 → 定时运行 → 邮件/机器人推送；
- 关键动作：配置成员映射、验证首次推送、观察运行摘要；
- 阻力来源：担心被监控、担心内容失真——通过“来源可追溯、员工不确认即推送（CLI 形态）”简化流程，同时保留 `--print` 查看机制。

### 6.4 合规可行性

- 遵循最小必要原则，仅采集与工作产出直接相关的数据；
- 数据本地存储，不出域；
- 密钥仅环境变量注入，不入库、不入仓；
- 邮箱等个人信息在日志与失败原因中脱敏。

## 七、风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 生成内容不可追溯 | 无法核对条目来源 | 强制每条条目携带 `source_type` + `source_id`，拒绝 LLM 摘要（N-01） |
| 隐私与信任 | 员工抵触、担心监控 | 仅采集工作账号数据；来源可见；不采集私聊 |
| 平台依赖 | 飞书 API 变更/限流 | 抽象适配层；按异常类型分流重试；来源缺失时标注 |
| 采集不完整 | 漏掉线下工作 | CLI 形态下期主要通过邮件/机器人推送，成员可在群里补充说明 |
| 凭证泄露 | 安全合规风险 | 仅环境变量注入；`git grep` 扫描；敏感字段 `repr=False` |
| 重复触发 | 产生重复日报/邮件 | 数据库唯一约束 + `run_daily` 幂等检查 |

## 八、结论与建议

1. **需求成立**：日报是高频刚需，现有产品自动化程度低，“多源自动采集 + 可追溯生成”具备明确价值。
2. **本期定位**：以“研发团队工作痕迹 → 结构化日报”为最小闭环，形态为 Python CLI + 定时任务 + 邮件/飞书机器人推送。
3. **MVP 范围**：GitHub + 飞书任务 + 飞书消息 + 飞书考勤采集 → 个人/团队日报生成 → 邮件/飞书推送 → SQLite 历史存储。
4. **关键成功指标**：日报条目可追溯率 100%、定时任务成功率 ≥ 95%、无数据日仍生成、失败来源显式标注。
5. **下一步**：完成成员配置 → 配置 `.env` 凭证 → 手动试运行 → 设置定时任务 → 观察运行摘要与历史记录。
