## 第 1 章 概述

### 1.1 背景

团队成员的工作痕迹分散在 GitHub 提交、飞书任务流转、飞书群消息与飞书考勤中。写日报时依赖回忆与逐平台复制，存在条目遗漏、格式不一、协作成果归属不清、无法追溯原始记录等问题。本项目通过 API 自动采集上述数据，按成员归组生成个人与团队日报，经邮件与飞书机器人推送，并用 SQLite 保存历史，实现“数据自动长出来”。

### 1.2 总体目标

将“写日报”从人工回忆整理转变为**数据自动长出来**：在无需手工搬运数据的前提下，每工作日自动产出覆盖全组成员的格式统一日报，并可追溯每条日报条目的数据来源。

### 1.3 具体目标（均可度量）

| 编号 | 目标 | 度量指标 | 目标值 |
|---|---|---|---|
| G-01 | 日报自动化 | 需手工补写的成员占比 | ≤ 10%（每人每日手工补充 ≤ 1 条） |
| G-02 | 数据来源覆盖 | 采集成功的数据源数 / 计划数据源数 | = 4/4（GitHub、飞书任务、飞书消息、飞书考勤） |
| G-03 | 条目可追溯率 | 可回溯到原始记录的条目 / 全部条目 | = 100% |
| G-04 | 生成时效 | 定时触发到推送完成耗时（≤ 10 人组） | ≤ 5 分钟 |
| G-05 | 稳定性 | 连续 5 个工作日定时任务成功率 | ≥ 95%（允许单模块失败降级） |
| G-06 | 格式一致性 | 团队日报符合统一模板的字段完整度 | = 100% |
| G-07 | 数据留存 | 日报历史可查询天数 | ≥ 90 天 |

### 1.4 范围

#### 1.4.1 做什么

| 编号 | 范围条目 | 对应功能需求 | 说明 |
|---|---|---|---|
| R-01 | 采集 GitHub 提交记录 | FR-01 | 按 UTC 日区间、只读令牌、分页上限 |
| R-02 | 采集飞书任务流转 | FR-02 | 按日区间拉取任务状态变更 |
| R-03 | 采集飞书群消息 | FR-03 | 按日区间拉取群消息，撤回消息保留并标注 |
| R-04 | 生成个人日报 | FR-05 | 按成员归组，含无数据日标注 |
| R-05 | 生成团队日报 | FR-06 | 按成员分组汇总，格式统一，缺失成员显式标注 |
| R-06 | 邮件推送日报 | FR-07 | 逐收件人发送，部分失败隔离并返回结构化结果 |
| R-07 | 飞书机器人推送日报 | FR-08 | 群机器人 webhook 推送 |
| R-08 | SQLite 存储日报历史并支持查询 | FR-09 | 按日期 / 成员查询，保留 ≥ 90 天 |
| R-09 | 维护成员与采集映射配置 | FR-10 | 成员与 GitHub / 飞书账号映射，缺失不猜测 |
| R-10 | 定时触发全流程并保证幂等 | FR-11 | 同日同团队只允许一次成功运行 |
| R-11 | 采集飞书考勤数据并纳入日报 | FR-04 | 按日区间采集出勤/缺勤/迟到/请假记录，作为独立来源条目进入日报 |

#### 1.4.2 不做什么（本期明确排除）

| 编号 | 排除项 | 理由 |
|---|---|---|
| N-01 | 不做 AI 智能摘要/润色 | 生成内容不可核查，与“条目必须可追溯”冲突 |
| N-02 | 不做 Web 管理界面 | 本期以配置文件 + 命令行驱动，最小化实现面 |
| N-04 | 不做多团队租户隔离与权限体系 | 单团队部署，无多租户需求 |
| N-05 | 不做移动端 | 交付形态为定时任务 + 邮件/机器人 |

> 注：N-03“不采集考勤数据”已由 R-11 替代，考勤采集已纳入本期并完成。

### 1.5 术语

| 术语 | 定义 |
|---|---|
| 原始记录 | 从外部系统采集、未经归组的提交 / 任务 / 消息 / 考勤数据 |
| 条目（ReportItem） | 日报中的一条工作描述，必须携带 `source_type` 与 `source_id` |
| 个人日报 | `scope=PERSONAL` 的 `DailyReport`，`entity_id` 为 `member_id` |
| 团队日报 | `scope=TEAM` 的 `DailyReport`，`entity_id` 为 `team_id` |
| 运行摘要（RunSummary） | 一次 `run_daily` 的采集 / 生成 / 推送结果汇总 |
| 映射配置 | 成员与 GitHub 账号、飞书账号（任务 / 消息 / 考勤）的对应关系 |
| 端口（Port） | `Protocol` 定义的采集 / 推送抽象，真实与 Mock 实现可互换 |

## 第 2 章 业务流程

### 2.1 流程说明

每工作日 18:00，系统调度触发 `run_daily`：采集层从 GitHub 与飞书拉取当日数据并写入原始记录；生成层按成员归组生成个人日报，再汇总团队日报；推送层渲染并发送邮件与飞书消息；编排入口记录运行摘要并入库。

### 2.2 泳道图

![业务流程图](uml/业务流程图.png)

图源：`docs/uml/业务流程图.puml`（PlantUML）。关键控制点：

1. **幂等控制**：同日同团队只允许一次成功运行；
2. **失败隔离**：单采集源 / 单收件人失败不中断整批，失败项进入运行摘要；
3. **无数据日**：仍生成并推送，标注“无数据”，保证日报连续性；
4. **考勤来源**：v1.1 变更后，飞书考勤作为第四源接入，缺勤/迟到/请假条目显式标注。

### 2.3 异常流程

| 场景 | 处理 | 对用户可见结果 |
|---|---|---|
| GitHub 令牌失效 | 记录失败源，其余来源继续 | 日报标注“来源缺失：github”，摘要告警 |
| 飞书限流 | 退避重试 2 次 | 成功则无感；失败则标注来源缺失 |
| 某成员未配置映射 | 跳过该成员采集 | 日报标注“未配置映射成员” |
| 邮件部分失败 | 继续发送其余收件人 | 摘要列出失败收件人（脱敏） |
| 重复触发 | 跳过 | 无重复日报 |
| 考勤源未配置 | 整段跳过，行为与变更前一致 | 日报中无考勤条目 |

## 第 3 章 功能需求

### 3.1 涉众分析

| 涉众 | 角色 | 关注点 | 对需求的影响 |
|---|---|---|---|
| 团队成员 | 日报数据生产者 | 日报真实、无需手工补写、隐私边界清晰 | 条目必须可追溯；采集范围限于工作账号 |
| 主编（组长） | 日报汇总使用者 | 全组齐全、格式统一、可快速转发 | 团队日报固定结构；缺失成员显式标注 |
| 教师/企业导师 | 评审者 | 规范与实现一致、证据可追溯 | 保留运行摘要与历史记录 |
| 配置管理员 | 运维者 | 凭证安全、部署简单 | 密钥仅环境变量；单机 SQLite |
| 外部平台 | 数据提供方 | 限流、权限最小化 | 只读令牌；退避重试 |

| 编号 | 功能需求 | 对应用例 | 优先级 |

| FR-03 | 采集飞书群消息记录（含撤回标注） | UC-03 | 高 |
| FR-04 | 采集飞书考勤记录 | UC-04 | 高 |
| FR-05 | 生成个人日报（含无数据日处理） | UC-05 | 高 |
| FR-06 | 生成团队日报（按成员归组） | UC-06 | 高 |
| FR-07 | 邮件推送日报并返回发送结果 | UC-07 | 高 |
| FR-08 | 飞书机器人推送日报 | UC-08 | 中 |
| FR-09 | 日报历史存储与查询 | UC-09 | 中 |
| FR-10 | 成员与采集映射配置维护 | UC-10 | 中 |
| FR-11 | 定时触发全流程并保证幂等 | UC-11 | 高 |

### 3.3 用例图与用例模板

见附件《[用例图与用例模板](用例图与用例模板.md)》：包含用例图（PlantUML 源 `docs/uml/用例图.puml`）、参与者在列、11 个用例清单、UC-05/06/07/11 详细模板与其余简化用例。

### 3.4 需求优先级说明

- **中优先级**：UC-08~UC-10（增强可用性与运维）。
- 若工期压缩，可先交付高优先级闭环，但**不得**以“无数据日不生成”等方式削减可追溯性要求。

## 第 4 章 非功能性需求

### 4.1 性能

| 编号 | 指标 | 要求 |
|---|---|---|
| NFR-P1 | 单成员日报生成耗时 | ≤ 2 秒（原始记录 ≤ 500 条） |
| NFR-P2 | 全流程耗时（≤ 10 人） | ≤ 5 分钟 |
| NFR-P3 | 历史查询响应 | ≤ 1 秒（90 天数据量） |
| NFR-P4 | 采集分页上限 | 单源单日 ≤ 10 页，超出告警 |

### 4.2 安全

| 编号 | 要求 |
|---|---|
| NFR-S1 | GitHub 令牌、飞书凭证、SMTP 授权码一律通过环境变量注入，禁止入库与提交到仓库 |
| NFR-S2 | GitHub 令牌仅授予只读权限 |
| NFR-S3 | 日志不得输出令牌；邮箱等个人信息脱敏 |
| NFR-S4 | SQLite 访问一律参数化查询，禁止字符串拼接 SQL |
| NFR-S5 | 采集范围仅限团队成员的工作账号，不采集私聊内容 |

### 4.3 运行环境

| 项 | 要求 |
|---|---|
| 语言/运行时 | Python 3.12+ |
| 依赖管理 | uv |
| HTTP 客户端 | httpx ≥ 0.27 |
| 存储 | SQLite（标准库 `sqlite3`） |
| 操作系统 | Windows / Linux 单机运行 |
| 定时 | 系统计划任务（Windows）/ cron（Linux） |
| 网络 | 可访问 GitHub API、飞书开放平台、SMTP 服务 |

### 4.4 可靠性与可维护性

| 编号 | 要求 |
|---|---|
| NFR-R1 | 单模块失败不中断整批，失败项写入运行摘要 |
| NFR-R2 | 定时任务幂等：同日同团队只保留一次成功/部分成功运行 |
| NFR-R3 | 代码通过 ruff 静态扫描，零告警 |
| NFR-R4 | 接口契约变更须走变更审核并同步 `specs/` |

### 4.5 将来可能的需求（本期不做，预留）

1. AI 摘要与润色（需引入人工复核环节，与 N-01 冲突）。
2. Web 管理界面与多团队隔离（N-02 / N-04）。
3. 日报订阅与按项目维度统计。
4. 更多数据源（Jira、GitLab、禅道）。

## 第 5 章 数据需求

### 5.1 数据实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Member | `member_id`、`name`、`github_login`、`feishu_open_id`、`email`、`git_emails` | 成员与账号映射 |
| CommitRecord | `sha`、`author_login`、`message`、`committed_at(UTC)`、`repo`、`author_email` | GitHub 原始记录 |
| TaskRecord | `task_id`、`title`、`status`、`assignee_open_id`、`updated_at(UTC)` | 飞书任务原始记录 |
| MessageRecord | `msg_id`、`sender_open_id`、`content`、`created_at(UTC)`、`chat_id`、`is_recalled` | 飞书群消息原始记录 |
| AttendanceRecord | `record_id`、`member_open_id`、`work_date`、`status`、`checked_in_at(UTC)?`、`checked_out_at(UTC)?` | 飞书考勤原始记录 |
| DailyReport | `scope`、`entity_id`、`report_date`、`items`、`generated_at(UTC)`、`note` | 日报（个人/团队） |
| ReportItem | `source_type`、`source_id`、`text`、`occurred_at(UTC)` | 日报条目，可追溯 |
| RunSummary | `team_id`、`run_date`、`status`、`collected`、`sent`、`failed`、`started_at(UTC)`、`finished_at(UTC)?` | 运行摘要 |

### 5.2 数据流转

```text
GitHub API ──────┐
飞书任务 API ─────┼─→ 原始记录(SQLite 原始表) ─→ 归组/生成 ─→ DailyReport ─→ 渲染 ─→ 邮件/飞书推送
飞书消息 API ─────┤                                              │
飞书考勤 API ─────┘                                              └─→ 日报历史表 ─→ 查询

RunSummary ←────────────────────────────── 各层结果汇总 ──────┘
```

### 5.3 数据约束

1. 时间统一以 UTC 存储，展示按团队时区转换。
2. 每条日报条目必须包含 `source_type` 与 `source_id`（可追溯约束）。
3. 原始记录只追加、不修改；日报可重新生成但保留版本时间。
4. 成员映射缺失时不得猜测归属。
5. 考勤状态仅限于 `present`、`absent`、`late`、`leave`。

## 第 6 章 验收标准

| 编号 | 验收项 | 验收方法 | 通过标准 |
|---|---|---|---|
| AC-01 | 三/四源采集可用 | 使用测试团队运行采集 | 两日内数据 GitHub / 飞书任务 / 飞书消息 / 飞书考勤均成功写入 |
| AC-02 | 个人日报生成 | 对 3 名成员生成 | 条目完整、可追溯率 100%、无数据成员有标注 |
| AC-03 | 团队日报生成 | 生成团队日报 | 按成员分组、格式统一、缺失成员显式标注 |
| AC-04 | 邮件推送 | 向 3 个测试邮箱发送 | 全部送达；断网场景部分失败可隔离 |
| AC-05 | 飞书推送 | 群机器人推送 | 消息成功送达且格式正确 |
| AC-06 | 定时与幂等 | 同日触发两次 | 第二次被忽略，无重复日报 |
| AC-07 | 历史查询 | 查询近 30 天 | 结果正确、响应 ≤ 1 秒 |
| AC-08 | 安全合规 | 全仓检索 + 日志抽查 | 无硬编码令牌；日志无敏感信息 |
| AC-09 | 规范一致性 | 对照 `specs/` 检查 | 接口/数据模型无差异（与《设计与 specs 一致性检查记录》一致） |
| AC-10 | 考勤条目可追溯 | 生成含考勤日报 | 考勤条目 `source_type="feishu_attendance"` 且 `source_id` 非空，缺勤日有明确标注 |
