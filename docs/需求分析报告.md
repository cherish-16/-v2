## 第 1 章 概述

### 1.1 背景

团队成员的工作痕迹分散在 GitHub 提交、飞书任务流转与飞书群消息中，写日报时依赖回忆与逐平台复制，存在遗漏、格式不一、协作成果归属不清等问题。本项目通过 API 自动采集上述数据，自动生成个人与团队日报，经邮件与飞书机器人推送，并用 SQLite 保存历史。

### 1.2 总体目标

将“写日报”从人工回忆整理转变为**数据自动长出来**：在无需手工搬运数据的前提下，每工作日自动产出覆盖全组成员的格式统一日报，并可追溯每条日报条目的数据来源。

### 1.3 具体目标（均可度量）

| 编号 | 目标 | 度量指标 | 目标值 |
|---|---|---|---|
| G-01 | 日报自动化 | 需手工补写的成员占比 | ≤ 10%（每人每日手工补充 ≤ 1 条） |
| G-02 | 数据来源覆盖 | 采集成功的数据源数 / 计划数据源数 | = 3/3（GitHub、飞书任务、飞书消息） |
| G-03 | 条目可追溯率 | 可回溯到原始记录的条目 / 全部条目 | = 100% |
| G-04 | 生成时效 | 定时触发到推送完成耗时（≤ 10 人组） | ≤ 5 分钟 |
| G-05 | 稳定性 | 连续 5 个工作日定时任务成功率 | ≥ 95%（允许单模块失败降级） |
| G-06 | 格式一致性 | 团队日报符合统一模板的字段完整度 | = 100% |
| G-07 | 数据留存 | 日报历史可查询天数 | ≥ 90 天 |

### 1.4 范围

**做什么**：GitHub 提交采集、飞书任务采集、飞书消息采集、个人日报生成、团队日报生成、邮件推送、飞书机器人推送、SQLite 历史存储、定时编排、成员映射配置。

**不做什么**：

1. 不做 AI 智能摘要/润色（避免不可核查的生成内容）。
2. 不做 Web 管理界面（本期以配置文件和命令行驱动）。
3. 不采集考勤数据（列入 v1.1 迭代候选）。
4. 不做多团队租户隔离与权限体系（单团队部署）。
5. 不做移动端。

### 1.5 术语

| 术语 | 定义 |
|---|---|
| 原始记录 | 从外部系统采集、未经归组的提交/任务/消息数据 |
| 条目 | 日报中的一条工作描述，必须关联原始记录 |
| 团队日报 | 按成员分组汇总的全组日报 |
| 运行摘要（RunSummary） | 一次定时运行的采集/生成/推送结果汇总 |
| 映射配置 | 成员与 GitHub 账号、飞书账号（任务/消息）的对应关系 |

## 第 2 章 业务流程

### 2.1 流程说明

每工作日 18:00，系统调度触发 `run_daily`：采集层从 GitHub 与飞书拉取当日数据并写入原始记录；生成层按成员归组生成个人日报，再汇总团队日报；推送层渲染并发送邮件与飞书消息；编排入口记录运行摘要并入库。

### 2.2 泳道图

![业务流程图](uml/业务流程图.png)

图源：`docs/uml/业务流程图.puml`（PlantUML）。关键控制点：

1. 幂等控制：同日同团队只允许一次成功运行。
2. 失败隔离：单采集源/单收件人失败不中断整批，失败项进入运行摘要。
3. 无数据日：仍生成并推送，标注“无数据”，保证日报连续性。

### 2.3 异常流程

| 场景 | 处理 | 对用户可见结果 |
|---|---|---|
| GitHub 令牌失效 | 记录失败源，其余来源继续 | 日报标注“来源缺失：GitHub”，摘要告警 |
| 飞书限流 | 退避重试 2 次 | 成功则无感；失败则标注来源缺失 |
| 某成员未配置映射 | 跳过该成员采集 | 日报标注“未配置映射成员” |
| 邮件部分失败 | 继续发送其余收件人 | 摘要列出失败收件人 |
| 重复触发 | 跳过 | 无重复日报 |

## 第 3 章 功能需求

### 3.1 涉众分析

| 涉众 | 角色 | 关注点 | 对需求的影响 |
|---|---|---|---|
| 团队成员 | 日报数据生产者 | 日报真实、无需手工补写、隐私边界清晰 | 条目必须可追溯；采集范围限于工作账号 |
| 主编（组长） | 日报汇总使用者 | 全组齐全、格式统一、可快速转发 | 团队日报固定结构；缺失成员显式标注 |
| 教师/企业导师 | 评审者 | 规范与实现一致、证据可追溯 | 保留运行摘要与历史记录 |
| 配置管理员 | 运维者 | 凭证安全、部署简单 | 密钥仅环境变量；单机 SQLite |
| 外部平台 | 数据提供方 | 限流、权限最小化 | 只读令牌；退避重试 |

| FR-09 | 成员与采集映射配置维护 | UC-09 | 中 |

### 3.3 用例图与用例模板

见附件《[用例图与用例模板](用例图与用例模板.md)》：包含用例图（PlantUML 源 `docs/uml/用例图.puml`）、参与者在列、10 个用例清单、UC-04/05/06/10 详细模板与其余简化用例。

- 高优先级：UC-01~06、UC-10（构成“采集 → 生成 → 推送”最小闭环）。
- 中优先级：UC-07~09（增强可用性与运维）。
- 若工期压缩，可先交付高优先级闭环，但**不得**以“无数据日不生成”等方式削减可追溯性要求。

## 第 4 章 非功能性需求

### 4.1 性能

| 编号 | 指标 | 要求 |
|---|---|---|
| NFR-P1 | 单成员日报生成耗时 | ≤ 2 秒（原始记录 ≤ 500 条） |
| NFR-P2 | 全流程耗时（≤ 10 人） | ≤ 5 分钟 |
| NFR-P3 | 历史查询响应 | ≤ 1 秒（90 天数据量） |
| NFR-P4 | 采集分页上限 | 单源单日 ≤ 10 页，超出告警 |

### 4.2 安全

| 编号 | 要求 |
|---|---|
| NFR-S1 | GitHub 令牌、飞书凭证、SMTP 授权码一律通过环境变量注入，禁止入库与提交到仓库 |
| NFR-S2 | GitHub 令牌仅授予只读权限 |
| NFR-S3 | 日志不得输出令牌；邮箱等个人信息脱敏 |
| NFR-S4 | SQLite 访问一律参数化查询，禁止字符串拼接 SQL |
| NFR-S5 | 采集范围仅限团队成员的工作账号，不采集私聊内容 |

### 4.3 运行环境

| 项 | 要求 |
|---|---|
| 语言/运行时 | Python 3.12+ |
| 依赖管理 | uv |
| 存储 | SQLite（标准库 `sqlite3`） |
| 操作系统 | Windows / Linux 单机运行 |
| 定时 | 系统计划任务或进程内调度 |
| 网络 | 可访问 GitHub API、飞书开放平台、SMTP 服务 |

### 4.4 可靠性与可维护性

| 编号 | 要求 |
|---|---|
| NFR-R1 | 单模块失败不中断整批，失败项写入运行摘要 |
| NFR-R2 | 定时任务幂等：同日同团队只保留一次成功运行 |
| NFR-R3 | 代码通过 ruff/flake8 静态扫描，零告警 |
| NFR-R4 | 接口契约变更须走变更审核并同步 `specs/` |

### 4.5 将来可能的需求（本期不做，预留）

1. 考勤数据采集（v1.1 变更演练场景）。
2. AI 摘要与润色（需引入人工复核环节）。
3. Web 管理界面与多团队隔离。
4. 日报订阅与按项目维度统计。

## 第 5 章 数据需求

### 5.1 数据实体

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Member | id、name、feishu_id、github_login | 成员与账号映射 |
| CommitRecord | sha、author、message、committed_at(UTC)、repo | GitHub 原始记录 |
| TaskRecord | task_id、title、status、assignee、updated_at | 飞书任务原始记录 |
| MessageRecord | msg_id、sender、content、created_at、chat_id | 飞书群消息原始记录 |
| DailyReport | scope、entity_id、date、items、generated_at | 日报（个人/团队） |
| RunSummary | run_date、collected、generated、sent、failed、status | 运行摘要 |

### 5.2 数据流转

```text
GitHub API ──┐
飞书任务 API ─┼─→ 原始记录(SQLite 原始表) ─→ 归组/生成 ─→ DailyReport ─→ 渲染 ─→ 邮件/飞书推送
飞书消息 API ─┘                                              │
                                                             └─→ 日报历史表 ─→ 查询
RunSummary ←────────────────────────────── 各层结果汇总 ──────┘
```

### 5.3 数据约束

1. 时间统一以 UTC 存储，展示按团队时区转换。
2. 每条日报条目必须包含 `source_type` 与 `source_id`（可追溯约束）。
3. 原始记录只追加、不修改；日报可重新生成但保留版本时间。
4. 成员映射缺失时不得猜测归属。

## 第 6 章 验收标准

| 编号 | 验收项 | 验收方法 | 通过标准 |
|---|---|---|---|
| AC-01 | 三源采集可用 | 使用测试团队运行采集 | 两日内数据三源均成功写入 |
| AC-02 | 个人日报生成 | 对 3 名成员生成 | 条目完整、可追溯率 100%、无数据成员有标注 |
| AC-03 | 团队日报生成 | 生成团队日报 | 按成员分组、格式统一、缺失成员显式标注 |
| AC-04 | 邮件推送 | 向 3 个测试邮箱发送 | 全部送达；断网场景部分失败可隔离 |
| AC-05 | 飞书推送 | 群机器人推送 | 消息成功送达且格式正确 |
| AC-06 | 定时与幂等 | 同日触发两次 | 第二次被忽略，无重复日报 |
| AC-07 | 历史查询 | 查询近 30 天 | 结果正确、响应 ≤ 1 秒 |
| AC-08 | 安全合规 | 全仓检索 + 日志抽查 | 无硬编码令牌；日志无敏感信息 |
| AC-09 | 规范一致性 | 对照 `specs/` 检查 | 接口/数据模型无差异（与《设计与 specs 一致性检查记录》一致） |
