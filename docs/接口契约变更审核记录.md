## 1. 审核依据与流程

1. 变更发起：开发工程师提交变更申请（说明变更前后契约、原因、影响范围）。
2. 影响分析：架构师对照 `specs/design.md`、`specs/tasks.md` 与已实现代码，评估对采集层 / 生成层 / 推送层 / 主编排入口的影响。
3. 审核判定：结论分为 **通过 / 有条件通过 / 驳回**；有条件通过须列出整改项与截止时间。
4. 同步更新：通过后由架构师更新 `specs/design.md` 接口契约章节，需求分析师同步 `specs/tasks.md` 验收标准，二者缺一不可。
5. 留痕：变更记录与本记录一同入库（Git 提交信息格式 `docs: [任务编号] 更新接口契约`）。

### CR-001　采集层：GitHub 提交采集（新增）

- **变更类型**：新增
- **所属任务**：T3-07（GitHub 提交采集模块）
- **发起人 / 日期**：开发工程师 / 2026-11-16
- **变更原因**：`design.md` 原契约缺少时间区间与分页参数，无法覆盖“按日采集”。

**变更前**：无（该接口为 v2 新增）。

**变更后**：

```python
# 采集层：github_collector.collect_commits
def collect_commits(
    owner: str,
    repo: str,
    since: datetime,          # 含，UTC
    until: datetime,          # 不含，UTC
    *,
    max_pages: int = 10,
) -> list[CommitRecord]:
    """返回区间内提交记录；空区间返回 []，不抛异常。"""
```

**影响分析**：

| 影响对象 | 影响说明 | 是否已同步 |
|---|---|---|
| `design.md` 接口契约 | 新增函数签名与异常约定 | 是 |
| `tasks.md` T3-07 验收标准 | 新增“空区间返回空列表”用例 | 是 |
| 生成层 | 仅消费 `CommitRecord`，字段不变 | 无需变更 |
| 测试用例 | 新增 UTC 边界、分页截断两类用例 | 是 |

**审核意见**：签名与 `design.md` 分层职责一致；时间参数统一 UTC 并在注释中写明“含/不含”，可避免跨时区重复采集。**通过**。

**复核记录**：2026-11-25 架构师复核，契约已并入 `specs/design.md` §3.1，实现见 `collectors/github.py:34`。

### CR-002　生成层：日报生成入口（修改）

- **变更类型**：修改
- **所属任务**：T3-10（日报生成）
- **发起人 / 日期**：开发工程师 / 2026-11-17
- **变更原因**：个人日报与团队日报需共用生成逻辑，原契约只支持个人。

**变更前**：

```python
def generate_report(member_id: str, report_date: date) -> DailyReport: ...
```

**变更后**：

```python
class ReportScope(str, Enum):
    PERSONAL = "personal"
    TEAM = "team"

def generate_report(
    scope: ReportScope,
    entity_id: str,           # 个人：member_id；团队：team_id
    report_date: date,
) -> DailyReport: ...
```

**影响分析**：

| 影响对象 | 影响说明 | 处理 |
|---|---|---|
| `design.md` 数据模型 | `DailyReport` 需增加 `scope` 字段 | 已更新 |
| `tasks.md` T3-10 | 用例拆分为个人 / 团队两组 | 已更新 |
| 主编排入口 | 调用方需传 `scope`，原两处调用点已改 | 已改 |
| 推送层 | 不感知 scope，仅消费渲染结果 | 无需变更 |

**审核意见（有条件通过）**：

1. 同意统一入口，避免两套生成逻辑漂移。
2. **整改项一**：`DailyReport.scope` 的默认值不得隐式设为 `PERSONAL`，必须显式传入，防止团队日报被误标。
3. **整改项二**：在 `design.md` 补充“空数据日”的行为约定（无采集记录时仍生成条目并标注“无数据”）。
4. 整改完成后由架构师复核，方可合并。

**整改与复核**：2026-11-25 由 T3-10 提交实现（`generate_report` 的 `scope` 为无默认值必填参数，`builder.py:91`），空数据日返回 `note="无数据"` 的日报而非 `None`；架构师复核**通过**。

### CR-003　推送层：邮件推送（修改）

- **变更类型**：修改
- **所属任务**：T3-13（邮件推送）
- **发起人 / 日期**：开发工程师 / 2026-11-18
- **变更原因**：SMTP 偶发超时，原契约直接抛异常，导致单封失败中断整批推送。

**变更前**：

```python
def send_email(report: DailyReport, recipients: list[str]) -> None: ...
```

**变更后**：

```python
@dataclass
class SendResult:
    success: list[str]
    failed: list[tuple[str, str]]   # (收件人, 失败原因)

def send_email(report: DailyReport, recipients: list[str]) -> SendResult:
    """单封失败不中断整批；全部失败时 failed 覆盖全部收件人。"""
```

**影响分析**：

| 影响对象 | 影响说明 | 处理 |
|---|---|---|
| `design.md` 接口契约 | 返回值由 `None` 改为 `SendResult` | 已更新 |
| `tasks.md` T3-13 | 新增“部分失败仍继续”验收用例 | 已更新 |
| 主编排入口 | 需记录 `SendResult.failed` 到日志 | 已改 |
| 非功能性约束 | 重试次数沿用 ADR-003（最多 2 次） | 已对齐 |

**审核意见**：返回结构化结果优于抛异常，符合“单模块失败不拖垮全流程”的设计原则；异常语义与 ADR-003 一致。**通过**。

**复核记录**：2026-11-25 契约已并入 `specs/design.md` §3.4，实现见 `publishers/email.py:44`。

### CR-004　采集层：飞书任务采集分页（新增）— 驳回

- **变更类型**：新增
- **所属任务**：T3-08（飞书任务采集）
- **发起人 / 日期**：开发工程师 / 2026-11-19
- **变更原因**：希望新增 `page_size`、`cursor` 两个对外参数，便于测试。

**审核意见（驳回）**：

1. 分页游标属于**实现细节**，不应暴露到业务契约层；调用方只需“按日取全量”，分页应在模块内部完成。
2. 对外契约保持 `collect_tasks(since, until) -> list[TaskRecord]` 不变。
3. 若确需调试手段，应新增**内部函数**或在测试中以注入方式解决，不得改动 `design.md` 公共契约。
4. 结论：**驳回**，维持原契约；由发起人更新实现方案后重新提交（本次不产生契约变更）。

**复核记录**：2026-11-25 发起人确认撤回，CR-004 关闭，不纳入版本。实现中分页完全内部化（`collectors/feishu.py:60`），对外契约未变。
