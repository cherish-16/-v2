## 第1章 分析概述与技术目标

### 1.1 项目背景与定位

本项目为软件工程职业技能实践课程设计“智能日报生成器”的第二个迭代（v2.0）。系统面向小型研发团队，解决三个手工日报痛点：信息散落在 GitHub 与飞书两个平台、成员口头汇报易漏项、负责人汇总耗时且口径不一。

系统每个工作日定时触发一次：从 GitHub 拉取当日提交、从飞书拉取任务与群消息（v1.1 起可选接入飞书考勤），按成员归组生成每人一份个人日报与一份团队日报，经邮件与飞书群机器人两个渠道推送，并把全部原始记录、日报与运行摘要落库 SQLite，支持历史查询与重复触发防护。

### 1.2 技术目标

结合 proposal 的范围条目与 design.md 的非功能需求，本迭代确立六项可验证的技术目标：

| 编号 | 技术目标 | 含义与判定口径 |
|---|---|---|
| T-1 | 时间正确性 | 全部时间统一归一为 UTC aware 存储，展示按团队时区转换；“团队时区的一天”换算为 UTC 半开区间 `[start, end)`，杜绝跨时区重复或漏采 |
| T-2 | 幂等性 | 同一团队同一天只允许一次有产出（`success`/`partial`）的运行；重复触发返回 `skipped`，不产生重复日报与重复邮件，`--force` 可显式重跑 |
| T-3 | 失败隔离 | 任一采集源、任一成员日报、任一推送渠道失败均不中断整体流程，失败项记入 `RunSummary.failed` 并反映在状态判定中 |
| T-4 | 可追溯性 | 每条日报条目必须携带非空 `source_type` + `source_id`，可回溯到原始提交 / 任务 / 消息 / 考勤记录 |
| T-5 | 可维护性 | 四层架构 + 端口适配器；依赖方向由 `tests/test_architecture.py` 自动守护 |
| T-6 | 安全合规 | 密钥只经 `config.py` 读取且 `repr` 脱敏；SQL 全部参数化；日志与失败原因中的邮箱一律脱敏 |

### 1.3 技术选型与运行环境

| 类别 | 选型 | 理由 |
|---|---|---|
| 语言 | Python ≥ 3.12 | `StrEnum` / `datetime.UTC` 等新特性简化枚举与时区处理 |
| HTTP | httpx ≥ 0.27 | 同步 Client 满足定时批处理；超时与重试统一收口于 `net.py` |
| 存储 | SQLite（标准库 sqlite3） | 单机零运维；部分唯一索引直接表达幂等约束 |
| 时区 | 标准库 zoneinfo + tzdata | Windows 亦可用，无第三方依赖 |
| 命令行 | argparse（标准库） | 子命令简单，无需引入 click |
| 邮件 | smtplib（标准库） | `SMTP_SSL` 足够，避免额外依赖 |
| 测试 | pytest ≥ 8 + pytest-cov | 单元 / 集成 / 架构守护 / 回归四层测试 |
| 静态检查 | ruff（E/F/I/UP/B 规则集） | 统一风格，行宽 100 |

### 1.4 分析方法与报告范围

本报告以 `specs/proposal.md`（范围与成功标准）、`specs/design.md`（架构与数据模型）为基准，对照 `src/daily_report` 实际代码逐模块核对后编写，图示与代码保持一致。本期实现为“命令行 + 定时任务 + 邮件/飞书机器人推送”的最小可行形态：不包含 AI 摘要、Web 管理界面、多租户与移动端（见 `docs/业务调研报告.md` 1.4 节与 `docs/需求分析报告.md` 1.4 节）。后续章节依次给出：四层架构与模块划分（第 2 章）、对象与类建模含类图和关键序列图（第 3 章）、数据结构设计含 ER 图与 SQLite 表结构（第 4 章）、各模块函数级接口契约（第 5 章）、由验收标准导出的测试方案（第 6 章）。

## 第2章 系统架构与模块划分（四层结构）

### 2.1 四层总体结构

系统采用“分层 + 端口适配器（轻量）”架构风格，划分为四个业务层：主编排入口层、采集层、生成层（含渲染）、推送层；另有共享基础层（models、errors、config、net、storage）被所有层依赖。

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 主编排入口层  orchestration/run_daily.py · cli.py                    │
│   幂等检查 → 采集 → 生成 → 渲染 → 推送 → 写运行摘要                  │
└───────┬──────────────────────┬──────────────────────┬───────────────┘
        │                      │                      │
┌───────▼────────┐    ┌───────▼────────┐    ┌───────▼───────────────┐
│ 采集层          │    │ 生成层          │    │ 推送层                 │
│ collectors/     │    │ generation/     │    │ publishers/            │
│   github        │    │   attribution   │    │   email                │
│   feishu        │    │   builder       │    │   feishu_bot           │
│   mock          │    │ render/text     │    │   fake                 │
└───────┬────────┘    └───────┬────────┘    └───────┬───────────────┘
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │
                    ┌─────────▼─────────┐
                    │ 共享基础层          │
                    │ models · errors     │
                    │ config · net        │
                    │ storage             │
                    └─────────────────────┘
```

### 2.2 各层职责与依赖规则

| 层 | 职责 | 允许依赖 |
|---|---|---|
| 主编排入口层 | 串联全流程、幂等控制、失败隔离、汇总 `RunSummary`；`cli.py` 负责参数解析与退出码 | 采集层 + 生成层 + 推送层 + 共享基础层 |
| 采集层 | 对接 GitHub REST 与飞书开放平台，产出领域记录；mock 实现与真实实现同契约 | 共享基础层 |
| 生成层 | 纯函数归组与日报构建；渲染层只管呈现不做数据加工 | 共享基础层 |
| 推送层 | 把渲染结果投递到邮件 / 飞书渠道，返回结构化结果；不生成内容 | 共享基础层 |
| 共享基础层 | 领域模型、异常、配置、网络与持久化等横切能力 | 仅标准库与 httpx |

**依赖方向约束**：采集层、生成层、推送层只依赖共享基础层；只有 `orchestration/` 可以同时依赖三者。任何下层模块反向 import 上层视为分层违规，由 `tests/test_architecture.py` 在每次测试时自动检查。

### 2.3 模块清单与职责边界

| 模块 | 职责边界（一句话） |
|---|---|
| `config.py` | 从环境变量与 `.env` 装配全部配置；是密钥的唯一读取点，不读其他文件、不访问网络 |
| `models.py` | 全部领域数据结构；构造时归一 UTC，无业务逻辑、无 IO |
| `errors.py` | 异常类型体系；不含处理策略 |
| `net.py` | HTTP 调用统一 10s 超时与按异常类型分流的重试（ADR-003） |
| `members.py` | 成员 JSON 文件的加载与校验 |
| `storage/schema.py` | 建表 DDL（全部 `IF NOT EXISTS` 幂等）与 `init_db` |
| `storage/repository.py` | 原始记录与日报的持久化、查询；全项目唯一写 SQL 的模块 |
| `collectors/base.py` | 四个采集端口 `Protocol` 与 `SourceBundle` 定义 |
| `collectors/github.py` | GitHub REST 提交采集（分页 + 分支过滤）；只产出 `CommitRecord` |
| `collectors/feishu.py` | 飞书任务 / 消息 / 考勤采集（tenant_token 缓存）；只产出对应记录 |
| `collectors/mock.py` | 离线演示数据源；与真实实现同契约，窗口过滤语义一致 |
| `generation/attribution.py` | 原始记录 → 成员归组；映射缺失不猜测，纯函数无 IO |
| `generation/builder.py` | 归组结果 → `DailyReport`（个人 / 团队）；条目可追溯约束在此强制 |
| `render/text.py` | `DailyReport` → 纯文本 / 邮件 HTML / 团队分组文本；纯函数 |
| `publishers/base.py` | `EmailPublisher` / `BotPublisher` 端口与 `SendResult` / `PushResult` |
| `publishers/email.py` | `SMTP_SSL` 推送；单收件人失败隔离、认证失败整批停止、邮箱脱敏 |
| `publishers/feishu_bot.py` | 群机器人 webhook 推送 |
| `publishers/fake.py` | 可注入失败的测试替身 |
| `orchestration/run_daily.py` | 编排入口：幂等、隔离、状态判定、运行摘要落库 |
| `cli.py` | `members import/list` 与 `run` 两个子命令；退出码 0/1/2 |

### 2.4 关键架构决策（ADR 摘要）

| 编号 | 决策 | 理由与效果 |
|---|---|---|
| ADR-003 | HTTP 按异常类型分流重试：401/403 直接抛 `AuthenticationError` 不重试；429/5xx 指数退避重试；其它 4xx 抛 `TransientError` 不重试 | 认证失败重试只会放大无效请求；同请求重发不会有不同结果 |
| ADR-005 | 考勤作为第四类数据源，新增独立 `AttendanceSource` 端口，`SourceBundle` 中以可选字段注入 | 不修改既有 `collect_tasks` 语义（单一职责）；未配置考勤时行为与 v2.0 完全一致，实现只改一个装配点 |
| 幂等约束 | `run_summaries` 上建部分唯一索引 `(team_id, run_date) WHERE status IN ('success','partial')` | `success` 与 `partial` 都已产生推送，必须唯一以防重触发二次发信；`failed` 不受限，全渠道失败后允许当日重试 |
| 降级保护 | `daily_reports` 的 upsert 带 `WHERE`：新报告条目数不少于已存报告才允许覆盖 | 采集源临时失败时重新生成，不会把好日报冲成“无数据” |
| 配置收口 | `config.py` 是密钥唯一读取点；敏感字段 `repr=False` | 日志与 traceback 不泄露令牌；测试显式传 `env` 可完全隔离 `.env` |

### 3.5 对象不变式汇总

| 不变式 | 强制位置 |
|---|---|
| 所有 `datetime` 字段必须 UTC aware，构造时归一为 UTC | `models.ensure_utc`，各记录 `__post_init__` |
| naive datetime 一律拒绝（`ValueError`） | 同上 |
| `ReportItem.source_id` 非空，否则 `TraceabilityError` | `models` 与 `builder._require` |
| `AttendanceRecord.status ∈ {present, absent, late, leave}` | `models.ATTENDANCE_STATUSES` |
| `AttendanceRecord.record_id` 非空（可追溯） | `models.__post_init__` |
| `RunSummary.status ∈ {success, skipped, partial, failed}` | `models.__post_init__` |
| `DailyReport.scope` 必填、无默认值 | `builder.generate_report` 签名 |
| 无数据日返回带 `note="无数据"` 的日报，绝不返回 `None` | `builder._compose_note` |
| 考勤记录 `checked_in/out_at` 为 `None` 表示未打点，不是数据缺失 | `models` 文档契约 + `builder` 渲染规则 |

## 第4章 数据结构设计（ER 图、SQLite 表结构）

### 4.1 概念模型与 ER 图

数据库共 6 张表。`members` 与三类原始记录之间是“账号映射”的逻辑归属关系（`github_login` / `feishu_open_id` / `git_emails` 字段匹配），刻意不建外键：原始记录以平台为准只追加落库，成员映射可随时补配并重新生成日报，归属运算在生成层（`attribution`）完成而非在库内完成。

```text
       members（逻辑归属中心）
       PK member_id
       github_login ──┐
       feishu_open_id │  账号映射（非外键）
       git_emails ────┘
              │
    ┌─────────┼─────────┐
    │         │         │
    ▼         ▼         ▼
commit_records  task_records  message_records
PK sha          PK task_id    PK msg_id
author_login    assignee_open_id  sender_open_id
author_email

┌──────────────────────┐      ┌────────────────────────────┐
│ daily_reports        │      │ run_summaries              │
│ id PK AUTOINCREMENT  │      │ id PK AUTOINCREMENT        │
│ (scope, entity_id,   │业务   │ (team_id, run_date)        │
│  report_date) UNIQUE │对应   │ 部分唯一索引 WHERE         │
│ body_json 含 source_id│     │ status IN ('success','partial')│
│ note：无数据/来源缺失 │      │ status ∈ 4 枚举             │
└──────────────────────┘      └────────────────────────────┘
```

**说明**：考勤记录（`AttendanceRecord`）当日采集后直接参与生成，不落库；飞书侧考勤接口为权威数据源，重复查询幂等，暂无本地持久化需求（v1.1 范围决策）。

### 4.2 SQLite 表结构

六张表的关键列与约束如下（时间列一律存 UTC ISO8601 字符串）：

| 表 | 列 | 约束与说明 |
|---|---|---|
| `members` | `member_id TEXT PK`；`name TEXT NOT NULL`；`github_login` / `feishu_open_id` / `email TEXT`；`git_emails TEXT`（JSON 数组） | `member_id` 唯一；`git_emails` 序列化为 JSON 以支持多邮箱归属 |
| `commit_records` | `sha TEXT PK`；`author_login` / `message` / `committed_at` / `repo NOT NULL`；`author_email TEXT` | `author_login` + `author_email` 双线索归属；`INSERT OR IGNORE` 按 `sha` 去重 |
| `task_records` | `task_id TEXT PK`；`title` / `status` / `updated_at NOT NULL`；`assignee_open_id TEXT` | 同上按 `task_id` 去重 |
| `message_records` | `msg_id TEXT PK`；`content` / `created_at` / `chat_id NOT NULL`；`sender_open_id TEXT`；`is_recalled INTEGER DEFAULT 0` | 撤回消息保留原文并打标记，日报中显示“[已撤回]”前缀 |
| `daily_reports` | `id INTEGER PK AUTOINCREMENT`；`scope` / `entity_id` / `report_date` / `generated_at` / `body_json NOT NULL`；`note TEXT` | `UNIQUE(scope, entity_id, report_date)`；upsert 带降级保护 `WHERE` |
| `run_summaries` | `id INTEGER PK AUTOINCREMENT`；`team_id` / `run_date` / `status` / `collected_json` / `sent_json` / `failed_json` / `started_at NOT NULL`；`finished_at TEXT` | 部分唯一索引 `idx_run_productive_unique` 保证生产性运行唯一 |

### 4.3 建表 DDL（`storage/schema.py`）

```sql
CREATE TABLE IF NOT EXISTS members (
    member_id      TEXT PRIMARY KEY,
    name           TEXT NOT NULL,
    github_login   TEXT,
    feishu_open_id TEXT,
    email          TEXT,
    git_emails     TEXT
);

CREATE TABLE IF NOT EXISTS commit_records (
    sha          TEXT PRIMARY KEY,
    author_login TEXT NOT NULL,
    message      TEXT NOT NULL,
    committed_at TEXT NOT NULL,
    repo         TEXT NOT NULL,
    author_email TEXT
);

CREATE TABLE IF NOT EXISTS task_records (
    task_id          TEXT PRIMARY KEY,
    title            TEXT NOT NULL,
    status           TEXT NOT NULL,
    assignee_open_id TEXT,
    updated_at       TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS message_records (
    msg_id           TEXT PRIMARY KEY,
    sender_open_id   TEXT,
    content          TEXT NOT NULL,
    created_at       TEXT NOT NULL,
    chat_id          TEXT NOT NULL,
    is_recalled      INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE IF NOT EXISTS daily_reports (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    scope        TEXT NOT NULL,
    entity_id    TEXT NOT NULL,
    report_date  TEXT NOT NULL,
    generated_at TEXT NOT NULL,
    body_json    TEXT NOT NULL,
    note         TEXT,
    UNIQUE (scope, entity_id, report_date)
);

CREATE TABLE IF NOT EXISTS run_summaries (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    team_id        TEXT NOT NULL,
    run_date       TEXT NOT NULL,
    status         TEXT NOT NULL,
    collected_json TEXT NOT NULL,
    sent_json      TEXT NOT NULL,
    failed_json    TEXT NOT NULL,
    started_at     TEXT NOT NULL,
    finished_at    TEXT
);

-- 幂等约束：同一团队同一天只允许一条「有产出」的记录
CREATE UNIQUE INDEX IF NOT EXISTS idx_run_productive_unique
    ON run_summaries (team_id, run_date)
    WHERE status IN ('success', 'partial');
```

### 4.4 运行参数与完整性策略

| 策略 | 实现 |
|---|---|
| 连接参数 | `PRAGMA foreign_keys=ON`；`PRAGMA journal_mode=WAL`（并发读不阻塞写） |
| SQL 纪律 | 全部语句参数化（`?` 占位），禁止字符串拼接（NFR-S4）；全项目仅 `repository.py` 写 SQL |
| 原始记录写入 | `INSERT OR IGNORE` 按主键幂等去重，只追加、不修改 |
| 日报写入 | `ON CONFLICT(scope, entity_id, report_date) DO UPDATE`，且新报告条目数 ≥ 已存条目数才覆盖（降级保护） |
| 运行摘要写入 | 先 `DELETE` 同键旧行再 `INSERT`（部分唯一索引无法被 `ON CONFLICT` 定位） |
| 序列化 | 日报整体序列化为 `body_json`（items 含 `source_type`/`source_id`/`text`/`occurred_at`）；`datetime` 存 ISO8601；读取时经 `fromisoformat` 还原为 UTC aware |

## 第5章 接口约定（各模块函数级契约）

本章按模块给出函数级契约。约定记法：前置条件为调用方必须保证的条件；异常列仅列本函数主动抛出的类型；被动传播的异常由编排层统一捕获隔离。

### 5.1 配置装配 `config.py`

| 函数 | 契约 |
|---|---|
| `load_settings(env=None, *, env_file=None) -> Settings` | 前置：无。优先级 显式 `env` > 进程环境变量 > `.env` 文件（当前目录 → 项目根）；显式传 `env` 时不读 `.env`（测试隔离）。后置：返回 frozen `Settings`。异常：`ConfigError`（`source_mode` 非法；live 模式缺 `GITHUB_TOKEN`；时区名无法被 `ZoneInfo` 解析；整型配置不是整数） |
| `Settings（dataclass, frozen）` | 字段：`source_mode` / `timezone` / `github_token` / `feishu_app_id` / `feishu_app_secret` / `smtp_host` / `smtp_port`(默认 465) / `smtp_user` / `smtp_password` / `feishu_bot_webhook` / `max_pages`(10) / `retry_times`(2) / `github_owner` / `github_repo` / `github_branch` / `insecure_tls` / `attendance_position`；敏感字段 `repr=False` |

### 5.2 领域模型 `models.py`

| 函数 | 契约 |
|---|---|
| `ensure_utc(value: datetime) -> datetime` | 前置：`value` 为 `datetime`。后置：返回 UTC aware。异常：`ValueError`（naive 输入） |
| 各 frozen 记录类构造 | `__post_init__` 归一时间并校验不变式（见 3.5 节）；违反即抛 `ValueError` |

### 5.3 采集端口 `collectors/base.py`

时间语义统一：`since` 含、`until` 不含（半开区间 `[since, until)`），且必须为 UTC aware。

| 端口 | 签名 | 后置 |
|---|---|---|
| `CommitSource` | `collect_commits(owner, repo, since, until, *, max_pages=10) -> list[CommitRecord]` | 仅返回窗口内提交；分页拉取至多 `max_pages` 页 |
| `TaskSource` | `collect_tasks(since, until) -> list[TaskRecord]` | 仅返回窗口内更新（飞书 epoch ms 已转 UTC） |
| `MessageSource` | `collect_messages(since, until) -> list[MessageRecord]` | 含撤回消息，`is_recalled` 标记 |
| `AttendanceSource` | `collect_attendance(since, until) -> list[AttendanceRecord]` | 可选端口；未配置时 `SourceBundle.attendance_source=None` |

### 5.4 网络层 `net.py`

| 函数 | 契约 |
|---|---|
| `get_json(client, url, *, params=None, headers=None, retry_times=2, sleep=time.sleep)` | GET 并解析 JSON，超时 10s。异常语义见下表 |
| `post_json(client, url, *, json_body, ...)` | 同 `get_json`，POST 语义 |
| `_classify(status)`（内部） | 401/403→auth；429 或 5xx→retry；其它→fail |

| 情形 | 处置 |
|---|---|
| HTTP 401 / 403 | 立即抛 `AuthenticationError`，不重试 |
| HTTP 429 / 5xx / 超时 / 传输错误 | 退避重试（1s、2s），共 `retry_times+1` 次尝试；耗尽后抛 `TransientError` |
| 其它 4xx | 抛 `TransientError`，不重试（重发不会有不同结果） |
| 成功（<400） | 返回 `response.json()` |

### 5.5 成员文件 `members.py`

| 函数 | 契约 |
|---|---|
| `load_member_file(path) -> list[Member]` | 读取 JSON 数组并逐条校验。异常：`MemberFileError`（条目非对象、必填字段缺失或为空）。`member_id`/`name` 必填，其余字段可选；`git_emails` 为字符串数组 |

### 5.6 存储层 `storage/`

| 函数 | 契约 |
|---|---|
| `init_db(path) -> sqlite3.Connection` | 打开或创建库，`foreign_keys=ON`、`journal_mode=WAL`，幂等执行全部 DDL |
| `Repository.upsert_members(members)` | `ON CONFLICT(member_id) DO UPDATE`；`git_emails` 序列化为 JSON |
| `Repository.list_members() -> list[Member]` | 按 `rowid` 序返回 |
| `Repository.save_commits / save_tasks / save_messages(records) -> int` | `INSERT OR IGNORE` 按主键去重；返回实际新增行数 |
| `Repository.save_report(report)` | 按 `(scope, entity_id, report_date)` upsert；新报告条目数 < 已存条目数时拒绝覆盖（降级保护） |
| `Repository.get_report(scope, entity_id, report_date) -> DailyReport \| None` | 按唯一键读取，`body_json` 反序列化 |
| `Repository.list_reports(since, until) -> list[DailyReport]` | 按 `report_date` 升序返回闭区间内的全部日报（历史查询，AC-07） |
| `Repository.save_run_summary(summary)` | 先删同键旧行再插入；触发部分唯一索引约束防生产性运行重复 |
| `Repository.find_latest_run(team_id, run_date) -> RunSummary \| None` | 返回最近一次运行（任意状态），幂等判定依据 |
| `Repository.find_successful_run(team_id, run_date) -> RunSummary \| None` | 仅返回 `status=success` 的运行 |

### 5.7 生成层 `generation/`

| 函数 | 契约 |
|---|---|
| `attribute(members, commits, tasks, messages, attendance=()) -> AttributionResult` | 纯函数。规则 1：映射缺失的成员列入 `unmapped`，绝不按姓名猜测归属；规则 2：提交优先按 `github_login` 归属，缺失时按 `git_emails` 小写匹配，任务 / 消息 / 考勤按 `feishu_open_id` 归属。`mapping_gaps` 按渠道记录半配置成员（如只配飞书未配 GitHub） |
| `generate_report(scope, entity_id, report_date, *, members, commits, tasks, messages, attendance=(), missing_sources=(), now=None, tz="Asia/Shanghai") -> DailyReport` | `scope` 必填无默认。后置：条目顺序固定为提交→任务→消息→考勤；`source_id` 非空否则 `TraceabilityError`；无数据日返回 note 含“无数据”的日报而非 `None`。`PERSONAL`：仅本人条目 + 本人映射缺口；`TEAM`：按 `members` 声明顺序汇总，条目文本加成员名前缀，无数据成员与未映射成员写入 note |

### 5.8 渲染层 `render/text.py`

三个函数均为纯函数：不修改入参、无 IO、不做数据加工。

| 函数 | 契约 |
|---|---|
| `render_text(report) -> str` | 标题 + 逐条“`[source_type] text`”+ 备注 |
| `render_email_html(report) -> str` | 邮件 HTML；所有插值经 `html.escape` |
| `render_team_text(report) -> str` | 按条目文本中第一个全角冒号前的成员名分组；切不出成员名的归入“其他” |

### 5.9 推送层 `publishers/`

| 接口 / 类 | 契约 |
|---|---|
| `EmailPublisher.send_email(report, recipients) -> SendResult` | `SendResult.success: list[str]`；`failed: list[(address, reason)]`；`ok` 属性 = 有成功送达 |
| `BotPublisher.push_to_feishu(report, webhook=None) -> PushResult` | `PushResult.ok: bool`；`error: str \| None` |
| `SmtpEmailPublisher.send_email` | 前置：`smtp_host`/`user`/`password` 齐备，否则 `ConfigError`。单收件人失败仅记录并继续；`SMTPAuthenticationError` 时整批停止、其余收件人标记 “`skipped: authentication failed`”；失败原因只记异常类型名（不转发可能含地址的异常文本，脱敏） |
| `WebhookBotPublisher.push_to_feishu` | 经 `net.post_json` 发送 webhook；网络异常向上传播，由编排层隔离 |
| `FakePublisher(fail_email=False, fail_bot=False)` | 测试替身，可注入渠道失败 |

### 5.10 编排入口 `orchestration/run_daily.py`

| 函数 | 契约 |
|---|---|
| `run_daily(team_id, report_date, *, settings, repo, sources, publishers, now=None, force=False) -> RunSummary` | 幂等：存在 `success`/`partial` 且未 `force` → 返回 `skipped` 摘要。采集窗口：团队时区当日 00:00–24:00 换算为 UTC 半开区间。隔离：逐源、逐成员、逐渠道 try/except。后置：`RunSummary` 必然落库 |
| `_day_window(report_date, tz_name)`（内部） | 返回 `(start, end) UTC`；时区名非法时告警并退回 UTC |

| `status` | 判定条件 |
|---|---|
| `skipped` | 当日已有 `success`/`partial` 运行且未指定 `force` |
| `failed` | 无成员配置（无产出，允许配置修正后重试）；或有推送渠道但邮件与飞书全部失败 |
| `partial` | 存在任一 `failed` 项，但仍有渠道成功（或未配置任何渠道） |
| `success` | 全部采集、生成与已配置渠道均成功 |

### 5.11 命令行 `cli.py`

| 子命令 | 参数 | 行为 |
|---|---|---|
| `members import` | `--file`（必填）、`--db` | 从 `members.json` 导入成员，打印导入数量 |
| `members list` | `--db` | 列出成员及缺失的映射字段 |
| `run` | `--team`（必填）、`--date`、`--print`、`--force`、`--demo`、`--db` | 执行 `run_daily` 并打印 JSON 摘要；`--date` 缺省取团队时区“今天”；`--demo` 使用内置三人演示数据，无需外部凭证；`--print` 渲染团队日报到终端 |

| 退出码 | 含义 |
|---|---|
| 0 | `success` / `partial` / `skipped`（含重复触发） |
| 1 | 运行失败（`failed`）、`ReportError`、成员文件错误、未配置成员 |
| 2 | 命令行参数错误 |

### 6.3 关键测试场景设计

| 场景 | 构造方式 | 断言要点 |
|---|---|---|
| 幂等与重跑 | 同一 `(team, date)` 连续调用 `run_daily`；再以 `force=True` 调用 | 第二次 `status=skipped`；`force` 后允许重新生成推送 |
| 失败隔离矩阵 | 单源抛异常 / 单成员数据异常 / `FakePublisher(fail_email, fail_bot)` 组合 | `failed` 字典逐项记录类型名；整体状态按 5.10 判定表落位 |
| 时区日窗口 | 跨 UTC 日期边界的时间戳（如北京时间次日 0:30） | `_day_window` 换算后 `[since, until)` 恰好覆盖团队时区全天 |
| 归属不猜测 | 成员仅配飞书未配 GitHub（及反向） | `mapping_gaps` 按渠道记录；note 写“未配置映射成员”，绝不按姓名匹配 |
| 降级保护 | 先生成含条目日报，再以空数据重新生成 | 条目更少的新报告不得覆盖已存报告 |
| 考勤语义（v1.1） | `present` / `late` / `absent` / `leave` / 未打点组合 | 缺勤与请假不显示时刻；迟到显示打点时间；`AttendanceSource` 未配置时行为与变更前一致 |
