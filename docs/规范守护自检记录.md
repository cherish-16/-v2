# 规范守护自检记录

| 项目 | 内容 |
|---|---|
| 阶段 | 阶段二 · 第 4 周 |
| 日期 | 2026-11-25 |
| 工具 | `scripts/check_spec_drift.py` |
| 检查逻辑 | 若 `src/**/*.py` 有改动而 `specs/` 与 `docs/` 均无改动，退出码 1 |

## 1. 脚本说明

```bash
python scripts/check_spec_drift.py --base <基准提交>
```

- `git diff --name-only <base> HEAD` 取改动清单
- 代码文件：前缀 `src/` 且后缀 `.py`
- 规范文件：前缀 `specs/` 或 `docs/`
- 有代码改动、无规范改动 → 提示漂移并退出 1

设计取舍：把 `docs/` 也算作规范改动，因为 §文档类交付物（一致性记录、变更演练记录）
承担了规范同步职责；只认 `specs/` 会误报。

## 2. 验证情形

### 情形 A：只改代码（应为漂移）

基准 `4cfd33c`（T4-01 变更单），HEAD 为 T4-03 考勤采集实现：

```bash
$ python scripts/check_spec_drift.py --base 4cfd33c
规范漂移：7 个代码文件有改动，但 specs/ 与 docs/ 均未更新：
  - src/daily_report/collectors/base.py
  - src/daily_report/collectors/feishu.py
  - src/daily_report/collectors/mock.py
  - src/daily_report/generation/attribution.py
  - src/daily_report/generation/builder.py
  - src/daily_report/models.py
  - src/daily_report/orchestration/run_daily.py

请先更新 specs/design.md 或 specs/proposal.md，再提交代码。
```

退出码 **1**。判定正确：本次提交是「按已批准的规范实现」，规范在上一提交已更新。

> 说明：这条规则比较的是**单次提交范围内**是否同时含代码与规范。本项目采用
> 「规范先行」——规范改动在 T4-01 提交，代码在 T4-03 提交，因此每次单独看都是
> 漂移。这是**刻意的顺序**，不是缺陷；脚本在这里的价值是提醒评审者「代码改动
> 必须有对应的规范出处」。实际评审时以 `变更涟漪演练记录.md` 的条目对应关系为准。

### 情形 B：规范与代码同改（应为通过）

基准 `431ac38`（T3 收尾），HEAD 含 `specs/` + `docs/` + 代码：

```bash
$ python scripts/check_spec_drift.py --base 431ac38
检查通过：代码改动 7 个，规范/文档改动 3 个。
```

退出码 **0**。

### 情形 C：只改文档

只改 `docs/` 的提交，脚本判定通过（`code` 为空，不触发规则）。

## 3. 接入方式建议

| 方式 | 命令 | 适用场景 |
|---|---|---|
| 手动 | `python scripts/check_spec_drift.py --base origin/feature` | 提交前自查 |
| Git hook | `.git/hooks/pre-push` 调用同上 | 推送前拦截 |
| CI | GitHub Actions 在 PR 上执行 `--base origin/main` | 合并门禁 |

本项目当前采用手动 + 评审时人工核对（见 `变更涟漪演练记录.md` 的影响面分析表）。

## 4. 已知局限

1. 按文件名前缀判断，不解析内容 —— 改了 `specs/` 里无关的错别字也会算「已同步」。
2. 不检查语义一致性（接口签名是否真的与代码一致），那部分依赖
   `设计与specs一致性检查记录.md` 的人工逐条核对。
3. 「规范先行」模式下逐提交检查必然报警，更适合用 `--base origin/main`
   做整分支检查。

## 5. 结论

脚本能正确区分「有规范改动」与「无规范改动」两种情形，退出码符合预期。
局限已记录，第 4 项说明决定了它应作为评审辅助而非硬门禁。
