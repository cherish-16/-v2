## 2. 参与者说明

| 参与者 | 类型 | 职责 | 关注点 |
|---|---|---|---|
| 团队成员（员工） | 主要 | 触发个人日报生成、维护自身映射配置 | 日报是否覆盖我当天真实工作；无需手工补写 |
| 主编（组长） | 主要 | 生成与查看团队日报、查询历史 | 全组条目齐全、格式统一、可直接转发 |
| 系统调度（定时任务） | 主要（系统） | 每工作日定时触发全流程 | 任务可重复执行、失败可追溯 |
| GitHub API | 外部系统 | 提供提交记录（只读） | 令牌最小权限、限流 |
| 飞书开放平台 | 外部系统 | 提供任务流转、群消息、机器人推送 | 凭证安全、消息格式 |
| SMTP 邮箱服务 | 外部系统 | 发送日报邮件 | 超时重试、失败隔离 |

## 4. 用例模板（详细）

### UC-04　生成个人日报

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-04 |
| 用例名称 | 生成个人日报 |
| 参与者 | 团队成员（主）、系统调度（主） |
| 目标 | 基于成员当日真实工作数据，自动生成一条个人日报 |
| 优先级 | 高 |
| 前置条件 | 成员已完成 GitHub / 飞书账号映射配置；采集层已取得当日原始记录 |
| 触发条件 | 成员手动触发，或系统调度在 18:00 触发 |
| 后置条件 | 生成一条 `DailyReport(scope=PERSONAL)` 并入库；原始记录未被修改 |
| 关联范围条目 | R-04；验收标准见《proposal 范围条目与用例可追溯对照表》 |
| 关联接口 | `generate_report(scope=PERSONAL, entity_id, report_date)` |

**主成功场景**

1. 系统读取该成员当日提交、任务、消息三类原始记录。
2. 系统按“提交 → 任务 → 消息”顺序整理为日报条目。
3. 系统为每条条目标注来源类型与来源标识（可追溯）。
4. 系统生成带日期、成员、条目列表的个人日报。
5. 系统将日报写入历史存储（UC-08）。
6. 系统返回生成结果与条目数。

**扩展场景**

| 编号 | 条件 | 处理 |
|---|---|---|
| 4a | 当日无任何原始记录 | 仍生成日报，条目区标注“无数据”，不返回空对象 |
| 2a | 同一提交对应多条任务 | 以提交为主条目，任务作为附加说明，避免重复计数 |
| 1a | 某一采集源失败 | 用其余来源生成日报，并在日报中标注“来源缺失：<源>” |

**业务规则**

- BR-04-1：条目必须可回溯到原始记录（来源类型 + 来源 ID）。
- BR-04-2：个人日报仅包含该成员自身数据，不串入他人记录。
- BR-04-3：日报日期以 UTC 存储，展示时按团队时区转换。

**非功能要求**

- 单成员生成耗时 ≤ 2 秒（数据量 ≤ 500 条原始记录）。
- 生成过程不得产生对外部系统的写操作。

### UC-05　生成团队日报

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-05 |
| 用例名称 | 生成团队日报 |
| 参与者 | 主编（主）、系统调度（主） |
| 目标 | 将全组成员条目汇总为格式统一的团队日报 |
| 优先级 | 高 |
| 前置条件 | 团队成员映射完整；各成员个人日报可生成 |
| 触发条件 | 主编手动触发，或系统调度在个人日报生成后触发 |
| 后置条件 | 生成一条 `DailyReport(scope=TEAM)` 并入库 |
| 关联范围条目 | R-05 |
| 关联接口 | `generate_report(scope=TEAM, entity_id=team_id, report_date)` |

**主成功场景**

1. 系统遍历团队全部成员并调用 UC-04 生成个人日报（`extend` 关系）。
2. 系统按成员分组汇总条目，组内按时间排序。
3. 系统生成团队汇总统计（参与人数、条目总数、无数据成员）。
4. 系统写入团队日报（UC-08）。
5. 系统返回团队日报与统计。

**扩展场景**

| 编号 | 条件 | 处理 |
|---|---|---|
| 1a | 某成员个人日报生成失败 | 记录失败成员，其余成员正常汇总，日报中标注“缺失成员” |
| 2a | 全组当日均无数据 | 生成团队日报并标注“全组无数据”，便于追溯 |

**业务规则**

- BR-05-1：协作成果按提交/任务与成员的关联关系归属，不按群消息发言者推测。
- BR-05-2：团队日报格式固定（成员 → 条目），不因成员数量变化而改变结构。

### UC-06　邮件推送日报

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-06 |
| 用例名称 | 邮件推送日报 |
| 参与者 | 系统调度（主）、SMTP 邮箱服务（外部） |
| 目标 | 将日报以统一 HTML 格式发送给指定收件人 |
| 优先级 | 高 |
| 前置条件 | 日报已生成；SMTP 凭证已通过环境变量注入 |
| 触发条件 | 系统调度在日报生成后触发 |
| 后置条件 | 发送结果记录到 `RunSummary`；失败收件人可追溯 |
| 关联范围条目 | R-06 |
| 关联接口 | `send_email(report, recipients) -> SendResult` |

**主成功场景**

1. 系统渲染日报为 HTML 邮件正文。
2. 系统逐一向收件人发送邮件。
3. 系统汇总成功与失败收件人，返回 `SendResult`。
4. 系统记录发送结果到运行摘要。

**扩展场景**

| 编号 | 条件 | 处理 |
|---|---|---|
| 2a | 单个收件人发送超时 | 按 ADR-003 最多重试 2 次，仍失败则记入 `failed`，继续下一位 |
| 2b | SMTP 认证失败 | 不重试，立即记入 `failed` 并告警，整批停止 |
| 1a | 日报为“无数据”版本 | 正常发送，正文标明无数据 |

**非功能要求**

- 单封邮件发送超时 ≤ 10 秒；整批（≤ 50 人）≤ 5 分钟。
- 日志中收件邮箱脱敏。

### UC-10　定时触发每日日报生成

| 字段 | 内容 |
|---|---|
| 用例编号 | UC-10 |
| 用例名称 | 定时触发每日日报生成 |
| 参与者 | 系统调度（主） |
| 目标 | 每工作日固定时间自动完成“采集 → 生成 → 推送”全流程 |
| 优先级 | 高 |
| 前置条件 | 配置完整；上一轮任务已结束（防重入） |
| 触发条件 | 工作日 18:00（团队时区） |
| 后置条件 | 产出 `RunSummary`；日报入库；推送结果可追溯 |
| 关联范围条目 | R-10 |
| 关联接口 | `run_daily(team_id, report_date) -> RunSummary` |

**主成功场景**

1. 系统检查是否已有同日成功运行记录，避免重复生成。
2. 系统依次执行 UC-01、UC-02、UC-03 采集。
3. 系统执行 UC-05 生成团队日报（内部经 UC-04）。
4. 系统执行 UC-06 与 UC-07 推送。
5. 系统写入 `RunSummary` 并结束。

**扩展场景**

| 编号 | 条件 | 处理 |
|---|---|---|
| 1a | 同日已成功运行 | 跳过并记录“重复触发已忽略”，不覆盖原日报 |
| 2a | 单个采集源失败 | 继续其余源，摘要中记录失败源 |
| 4a | 两个推送渠道均失败 | 保留已生成日报，摘要标记失败，次日可补推 |

**业务规则**

- BR-10-1：同一团队同一日期只允许一次成功运行（幂等）。
- BR-10-2：采集/推送模块之间不共享可写文件；编排层串行调用。

## 5. 用例关系说明

| 关系 | 源 | 目标 | 说明 |
|---|---|---|---|
| include | UC-10 | UC-01/02/03/04/05/06/07 | 定时流程必然执行各子流程 |
| include | UC-04、UC-05 | UC-08 | 生成后必然入库 |
| extend | UC-05 | UC-04 | 团队日报按成员汇总时扩展执行个人日报 |

## 6. 简化用例（次要用例）

| 编号 | 名称 | 主场景摘要 | 扩展摘要 |
|---|---|---|---|
| UC-01 | 采集 GitHub 提交记录 | 按 UTC 区间拉取提交并写入原始记录 | 空区间返回空列表；达到分页上限告警 |
| UC-02 | 采集飞书任务流转 | 拉取区间内任务变更并写入 | 接口限流时按 ADR-003 退避重试 |
| UC-03 | 采集飞书群消息 | 拉取区间内群消息并写入 | 消息被撤回时保留原记录并标注状态 |
| UC-07 | 飞书机器人推送日报 | 调用群机器人 webhook 发送 | webhook 失败重试 2 次后记入失败 |
| UC-08 | 存储与查询日报历史 | 日报入库；主编按日期/成员查询 | 查询无结果返回空列表 |
| UC-09 | 维护成员与采集映射配置 | 维护成员与 GitHub/飞书账号映射 | 映射缺失时该成员日报标注“未配置” |
